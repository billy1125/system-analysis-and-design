# 工單分派管理系統：修改需求提案書

> 老師提供一套已經在使用的[工單分派管理系統](../SAD-Work-Order/README.md)，現在工廠提出一項新需求。請先操作系統、讀懂它現在怎麼運作，再想清楚系統要怎麼改，寫成期末報告。

---

## 一、系統現況

某中型自行車零件加工廠的生管課，在 2026-10-01 用這套系統取代紙本工單：生管人員開立工單、派給工作中心，組長在系統上回報開工與完工，完工時填良品數與不良數。

工單看起來只是一張派工單，其實是生產現場的指令，也是生管掌握進度的依據。沒有做好工單管理，遇到下面兩種情況就很難處理：

- **現場做錯或空等**：做什麼產品、做多少、在哪個工作中心做、什麼時候要完成，都寫在工單上；工單錯了或沒派出去，現場就會做錯或空等。
- **回覆不了客戶交期**：哪些工單開工了、完工了沒有、良品與不良各多少，生管要靠這些數字安排下一批生產、回覆客戶交期。

紙本工單在現場傳來傳去，生管辦公室看不到即時進度，這是生管課改用系統的原因。

| 項目 | 現況 |
|---|---|
| 使用者 | 生管課的人員與各工作中心的組長。作業員不使用這套系統 |
| 使用地點 | 系統裝在生管課的一台電腦，生管辦公室與各工作中心的電腦以瀏覽器連線 |
| 規模 | 8 個畫面、4 張資料表、2 種角色 |
| 主要功能 | 未完工工單清單、開立工單、派工與改派、回報開工與完工、取消工單、工單查詢、產品與工作中心維護、帳號維護 |

## 二、修改需求

| 編號 | 需求 | 提出者 | 一句話說明要解決的問題 |
|---|---|---|---|
| CR-01 | 分批報工與工時 | 廠長 | 生產中看不到做了多少，完工時只有一個總數，也不知道花了多少工時 |

CR 是 Change Request（變更申請）的縮寫，實務上每一項系統修改都會編一個號碼，方便後續追蹤。

這一項是**新的需求**，不是修正錯誤。現行系統運作正常，只是當初沒有納入這個範圍。

## 三、CR-01 分批報工與工時

*本圖由 ChatGPT 生成，已由作者審核內容正確性*

### 3.1 原有系統的缺點

| 缺點 | 現場發生什麼事 |
|---|---|
| 生產中看不到做了多少 | 一張工單常要做好幾天，中間只有「生產中」三個字。生管人員想知道趕不趕得上交期，只能到現場問 |
| 跨班生產只能由一個人回報一次 | 夜班組長開工、早班組長完工，兩班各做了多少只能寫在完工備註裡 |
| 不記誰做、做了幾小時 | 不知道一張工單用了多少工時，下次排預定生產日只能憑經驗 |
| 不良數只有一個總數 | 不良原因寫在備註裡，想知道哪一種不良最多，只能一張一張讀 |

用任一帳號登入，打開 WO-261027-01：1200 件曲柄在 10-29 開工，交期是 11-06，只剩 1 天，系統上看不出已經做了幾件。再打開 WO-261020-01：夜班組長羅士傑在 10-22 晚上開工，早班組長曾國峰在 10-27 回報完工，完工備註寫著「早班 300、夜班 288；不良 12 件為夾痕」，兩班各做多少、為什麼不良，都只留在這段文字裡。WO-261005-01 的完工備註也是同樣的寫法。

### 3.2 可以改進的內容

1. 生產中可以分好幾次回報，每次記下良品數、不良數與回報時間
2. 每次回報記下是哪一班或哪些作業員做的、做了幾小時
3. 生管人員隨時看得到每張生產中工單的累計數量
4. 不良數依原因分類回報

### 3.3 改完之後要解決的問題

| 改完要做到 | 對應的缺點 |
|---|---|
| 生管人員不必到現場就知道一張工單做到哪裡 | 生產中看不到做了多少 |
| 每一班做了多少，在系統上分得開 | 跨班生產只能由一個人回報一次 |
| 一張工單用了多少工時查得到，可以拿來排下一次的預定生產日 | 不記誰做、做了幾小時 |
| 查得出哪一種不良最常發生 | 不良數只有一個總數 |

### 3.4 待小組決議的問題（必須將答案放在報告裡）

- 多久回報一次：每班一次、每做完一箱，還是組長自己決定？規定太細，組長會不會乾脆最後一次補
- 誰來回報：還是只有組長，還是作業員也要有帳號？作業員旁邊沒有電腦時怎麼辦
- 工時記到多細：每位作業員各自的時數，還是一班的總人時？機台的運轉時間要不要記
- 不良原因怎麼分類、由誰維護？選不到合適的原因時怎麼辦
- 累計數量到達工單數量時自動完工，還是組長要另外按完工
- 累計數量超過或不到工單數量時，系統怎麼處理
- 回報填錯了能不能修改或刪除？修改要留下紀錄嗎
- 上線以來已完工的工單只有一筆總數，改版後怎麼呈現

## 四、修改時的限制

| 限制 | 說明 |
|---|---|
| 技術不變 | 仍是 HTML + CSS + JavaScript，資料存在 SQLite 資料庫檔 |
| 可以新增 | 可以在既有資料表加欄位，也可以新增資料表 |
| 原有規則照舊 | 例如工單不得刪除、工單號的編碼方式不變、生管人員不能代替組長回報 |
| 範圍只到這一項 | 停工與恢復紀錄、多製程途程（一張工單依序經過好幾道製程）、自動排程與產能負荷計算、物料領用與庫存、不良品的重工與報廢、客戶訂單管理，這次不做 |
| 不必改程式 | 報告寫到需求、流程、資料與畫面為止。依你的修改建議實際改程式，是[額外投入加分](../../00-Course-Introduction/Bonus-Rules.md)的項目 |

## 五、你要交出什麼

期末報告分兩大部分：

| 部分 | 內容 |
|---|---|
| 第一部分：既有系統分析簡要報告 | 分析系統現在的樣子：背景與角色、現況流程、現況功能與需求、現況資料 |
| 第二部分：修改建議書 | 把這份提案書的修改需求，寫成正式的變更需求，再寫出修改前後的差異、會影響到哪裡、修改後的規格、資料與畫面怎麼改、怎麼驗收 |

這份提案書只說「要解決什麼問題」，不說「要怎麼改」。〈3.4〉的問題沒有標準答案，你的選擇與理由要寫進報告。每一項寫什麼、寫到多細，照[期末範例報告](../../04-Final-Project-Example-Reports/Final-Phase-Sample-Report.md)的結構。

## 六、名詞解釋

| 名詞 | 意思 |
|---|---|
| 工單 | 生產工單，生管要求現場做一批產品的指令，記載產品、數量與交期 |
| 工作中心 | 一群做同一類加工的機台與人員，例如 CNC 車削組、組裝線 |
| 製程 | 把材料加工成產品的其中一個步驟，例如車削、銑削、組裝 |
| 途程 | 一個產品依序要經過哪些製程、每一道在哪個工作中心做 |
| 派工 | 替工單選定由哪個工作中心、在哪一天生產 |
| 報工 | 現場回報生產的數量與狀況。**做完才報一次與分批報，生管看到的資訊不同** |
| 良品數、不良數、良率 | 良品數是合格的件數，不良數是不合格的件數；良率是良品數占兩者合計的比例 |
| 工時 | 做這張工單花掉的人力時間，常用「人時」計算，例如 3 個人做 2 小時是 6 人時 |
