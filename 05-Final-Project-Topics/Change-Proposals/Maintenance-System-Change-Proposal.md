# 設備保養紀錄管理系統：修改需求提案書

> 老師提供一套已經在使用的[設備保養紀錄管理系統](../SAD-Maintenance/README.md)，現在工廠提出一項新需求。請先操作系統、讀懂它現在怎麼運作，再想清楚系統要怎麼改，寫成期末報告。

---

## 一、系統現況

某中型金屬加工廠的設備課，在 2026-08-01 用這套系統取代設備旁的紙本保養表：主管替每台設備設定保養計畫，保養人員做完保養後在系統上逐項登錄結果，系統依上次保養日算出下次應保養日。

設備保養看起來只是例行工作，其實決定機台能不能穩定運轉，保養紀錄也是設備管理的依據。沒有做好保養管理，遇到下面兩種情況就很難處理：

- **機台突然故障**：保養延誤，機台容易在生產中途故障，停機會影響交期，也可能造成工安事故。
- **維修與汰換判斷**：哪台設備什麼時候保養、檢查結果如何、出過什麼問題，維修判斷與設備汰換都要看這份履歷。

貼在設備旁的紙本保養表容易遺失，也看不出哪些設備快到期，這是設備課改用系統的原因。

| 項目 | 現況 |
|---|---|
| 使用者 | 設備課的主管與保養人員。操作員不使用這套系統 |
| 使用地點 | 系統裝在設備課的一台電腦，廠內電腦以瀏覽器連線 |
| 規模 | 8 個畫面、5 張資料表、2 種角色 |
| 主要功能 | 待保養清單、逐項登錄保養結果、保養紀錄查詢、設備保養履歷、設備與保養計畫維護、帳號維護 |

## 二、修改需求

| 編號 | 需求 | 提出者 | 一句話說明要解決的問題 |
|---|---|---|---|
| CR-01 | 年度保養計畫與逾期紀錄 | 品保部 | 排不出全年的保養計畫，逾期過的那一次做完就看不出來 |

CR 是 Change Request（變更申請）的縮寫，實務上每一項系統修改都會編一個號碼，方便後續追蹤。

這一項是**新的需求**，不是修正錯誤。現行系統運作正常，只是當初沒有納入這個範圍。

## 三、CR-01 年度保養計畫與逾期紀錄

![CR-01 年度保養計畫與逾期紀錄](images/maintenance-annual-plan-comic.png)

*本圖由 ChatGPT 生成，已由作者審核內容正確性*

### 3.1 原有系統的缺點

| 缺點 | 現場發生什麼事 |
|---|---|
| 下次應保養日一律從上一次實際保養日往後推 | 每次晚幾天，日期就一路往後漂。客戶稽核要看「全年的保養計畫表」，系統排不出來，品保部只能另外用 Excel 排 |
| 逾期沒做的那一次不留紀錄 | 系統只看得到「現在逾期幾天」。保養做完之後，逾期的痕跡就消失了 |
| 沒有延期的申請與核准 | 產線趕貨不能停機時，保養人員自己往後延，主管事後才知道，理由頂多寫在備註裡 |
| 統計不出保養達成率 | 稽核問「這一季應做幾次、按時做了幾次」，沒有人答得出來 |

用主管帳號 `E5001` 登入，打開「設備」，點 EQ-001 看保養履歷：月保養原訂 2026-09-04 要做，因為趕貨拖到 09-24 才做，系統直接從 09-24 往後算下一次。這 20 天的逾期，只留在保養人員自己寫的備註裡。再看待保養清單上的 EQ-012：月保養原訂 2026-10-16 要做，到現在還沒做。只要有人登錄一次保養，它就會從逾期清單上消失，系統不會記得它曾經逾期。

### 3.2 可以改進的內容

1. 保養計畫排得出全年的應保養日期，可以印出或在畫面上看年度保養計畫表
2. 每一次應該保養都看得到結果：按時做、逾期才做、延期、還沒做
3. 產線不能停機時，保養人員可以申請延期，由主管核准，延期理由與核准人留在系統
4. 依期間與設備統計保養達成率

### 3.3 改完之後要解決的問題

| 改完要做到 | 對應的缺點 |
|---|---|
| 品保部不必另外用 Excel 排計畫，客戶稽核直接看系統 | 下次應保養日一路往後漂 |
| 逾期過的那一次事後查得到，逾期幾天也查得到 | 逾期沒做的那一次不留紀錄 |
| 延期事前就有人核准，事後查得到理由 | 沒有延期的申請與核准 |
| 稽核問達成率時，系統算得出來 | 統計不出保養達成率 |

### 3.4 待小組決議的問題（必須將答案放在報告裡）

- 下次應保養日要從原訂日往後推，還是從實際保養日往後推？如果兩種都要支援，要由誰決定，記在哪裡
- 月保養現在是每 30 天一次，不是每月固定一天。年度計畫表上的月保養要排在每月固定一天，還是每 30 天一次？每 30 天一次的話，一年會排出 12 或 13 次
- 「應該保養的那一次」要不要先存成一筆資料？如果要，什麼時候產生、要產生多遠以後的日期
- 主管改了保養週期，已經排好的未來日期要不要重排
- 延期可以延到哪一天、可以延幾次？延期之後，下一次從延後的日期還是原訂日起算
- 「按時」怎麼定義：一定要在原訂日當天，還是前後幾天內都算？提前做算不算按時
- 達成率的分母是什麼？停用的設備、延期核准過的那一次，要不要算進去
- 上線以來的舊紀錄沒有「原訂日」，改版後要怎麼補

## 四、修改時的限制

| 限制 | 說明 |
|---|---|
| 技術不變 | 仍是 HTML + CSS + JavaScript，資料存在 SQLite 資料庫檔 |
| 可以新增 | 可以在既有資料表加欄位，也可以新增資料表 |
| 原有規則照舊 | 例如保養紀錄不得刪除、登錄時保存當下的保養項目文字 |
| 範圍只到這一項 | 保養異常的追蹤列管、操作員的日常點檢、故障維修、依感測器資料決定保養時機，這次不做 |
| 不必改程式 | 報告寫到需求、流程、資料與畫面為止。依你的修改建議實際改程式，是[額外投入加分](../../00-Course-Introduction/Bonus-Rules.md)的項目 |

## 五、你要交出什麼

| 第二部分：修改建議書 | 把這份提案書的修改需求，寫成正式的變更需求，再寫出修改前後的差異、會影響到哪裡、修改後的規格、資料與畫面怎麼改、怎麼驗收 |
