# 期末題目

這個資料夾收錄期末小組報告（系統分析與修改建議）的五個題目。每一題是一套已經在工廠使用的管理系統，加上一份修改需求提案書，各組做哪一題由當堂公開抽籤決定。期末的情境、要交的 16 項內容與範例報告，完整規定見[報告內容](../00-Course-Introduction/Report-Contents.md)〈二、期末小組報告〉；抽籤方式見[SAD 課程介紹](../00-Course-Introduction/Course-Introduction.md)〈題目怎麼分配〉。

## 一、這些文件不會給你什麼

**不給既有系統的分析結果，也不給修改後的資料表、畫面與測試案例。**

系統的畫面、程式與資料庫都在，但流程圖、功能需求清單、ERD 與資料字典要你自己從系統整理出來，那是第一部分的工作。修改後長什麼樣，是第二部分的工作。

提案書的修改需求最後都有〈待小組決議的問題〉，會把要決定的問題攤開，但**不告訴你該選哪一個**。你們的選擇與理由，就是第二部分〈變更申請〉裡真正屬於你們的內容。

| 題目 | 領域 | 既有系統 | 修改需求提案書 | 修改需求 |

| 倉庫盤點管理系統 | 物料與倉儲 | [SAD-Inventory](Example-Systems/SAD-Inventory/README.md) | [修改需求提案書](Change-Proposals/Inventory-System-Change-Proposal.md) | CR-01 覆盤與差異核准 |
| 設備保養紀錄管理系統 | 設備維護 | [SAD-Maintenance](Example-Systems/SAD-Maintenance/README.md) | [修改需求提案書](Change-Proposals/Maintenance-System-Change-Proposal.md) | CR-01 年度保養計畫與逾期紀錄 |
| 員工教育訓練紀錄系統 | 人力資源與工安 | [SAD-Training](Example-Systems/SAD-Training/README.md) | [修改需求提案書](Change-Proposals/Training-System-Change-Proposal.md) | CR-01 應受訓與到期追蹤 |

五題的領域各不相同，修改需求也刻意錯開，因此不會有兩組交出結構相同的報告。

**五題共同的性質**：每套最多 5 張資料表、2–3 個角色；畫面用 HTML + CSS + JavaScript，一支 Node.js 小程式讀寫 SQLite 資料庫檔，在你自己的電腦上執行。每一題的修改需求都會同時動到流程、資料表與畫面。

範例報告的示範系統（工廠訪客進出登記系統）不在這五題之中，相關檔案見[報告內容](../00-Course-Introduction/Report-Contents.md)〈範例報告參考〉。

## 三、怎麼用這些文件

| 步驟 | 做什麼 |
|:--:|---|
| 1 | 抽到題目後，先讀該題的修改需求提案書，知道系統現在的狀況與工廠要改什麼 |
| 2 | 照該題系統的 `README.md` 安裝啟動，每一種角色都登入操作一遍 |
| 3 | 從系統整理出角色、流程、功能需求與資料，寫第一部分 |
| 4 | 回頭細讀提案書的修改需求。提案書會指出在系統上怎麼看到「原有系統的缺點」，先照著操作，確認自己看到的是同一個問題 |
| 5 | 把〈待小組決議的問題〉逐條做出決定，再開始寫第二部分 |

第 2 步不要跳過。沒操作過系統就動筆，第一部分會寫成想像中的系統，第二部分的影響分析也會跟著對不上。系統的資料玩壞了，重新下載即可，見各系統 `README.md`〈資料玩壞了怎麼辦〉。

## 四、你可以怎麼找答案

讀提案書或操作系統時一定會遇到不懂的地方。答案多半找得到，可以從下面幾個方向找：

1. **從系統本身找。** 操作時，每一種單據都從開立做到結案，邊做邊記：哪個角色能做什麼、資料在哪個畫面輸入、在哪個畫面看得到。這份筆記也是第一部分的材料。
2. **去找一張真的單子。** 五題在現場都有紙本或 Excel 的做法。用 Google 搜尋圖片或檔案，關鍵字如「異常處理單 範本」「盤點表 範本」「保養紀錄表 範本」「教育訓練簽到表 範本」「工單 範本」，可以直接看到大量實際的表單。拿來跟系統的畫面比：系統少了哪些欄位、多了哪些，每一欄是誰填、填了給誰看。答不出來的地方，就是要去問人的地方。
3. **找一位實習過的人問十分鐘。** 系上大三大四有實習過的學長姐、或修過相關課程的同學。問三個問題就夠了：這件事現在怎麼做、最常出錯的是哪一步、你覺得最麻煩的是什麼。
4. **把 AI 當成工業工程專家來問。** 先交代情境，再問現場的做法，例如：「你是有十年經驗的工廠品管工程師。一張品質異常單從開立到結案，現場通常會經過哪些步驟？哪一步最常卡住？」也可以把〈待小組決議的問題〉丟給它，請它說明各種做法在現場的優缺點。但 **AI 給的是一般工廠的做法，不是這一題的答案**：要拿回來跟系統與提案書對照，你自己要能說明為什麼採用。
5. **不要直接讓 AI 幫你規劃修改，自己卻說不出為什麼這樣規劃。** 先自己弄懂系統現在怎麼運作、這項修改要解決什麼，才看得懂 AI 規劃出來的東西、哪裡不適用於這一題。使用揭露義務見[SAD 課程介紹](../00-Course-Introduction/Course-Introduction.md)〈AI 工具使用揭露〉。

找到答案之後，把〈待小組決議的問題〉用自己的話重寫一次。寫不出來就是還沒懂。寫得出來，第二部分的〈變更申請〉就有一半的材料了。

## 五、如果讀完還是不懂

**這是正常的，不是你的問題。** 這些題目描述的是你還沒進去過的職場，看不懂的地方一定有。處理順序建議如下：

| 順序 | 做什麼 |
|:--:|---|
| 1 | 把不懂的地方寫成具體問題。「我不懂盤點」問不出東西，「盤點的時候倉庫還在出貨，那數字要怎麼算」才問得出東西 |
| 2 | 問修過相關課程的老師或實習過的同學。工管系的老師對這些現場流程都熟 |
| 3 | 直接問老師。問之前先照第 1 步把問題整理好，說得出卡在哪裡，不要只丟一句「老師，我都看不懂」 |
| 4 | 問 AI 幫你梳理概念，做法與限制見〈四〉第 4、5 點。**你必須看懂它給你的東西**，懂或不懂，會在口頭報告與個人訪談的問答裡直接顯現出來 |

**不要用「先寫下去再說」處理看不懂的部分。** 系統現況理解錯了，後面的修改建議會一路錯到底，而且訪談時一問就出來。

## 六、有幾件事這五題都不要做

不管抽到哪一題，下面這些方向都會讓報告偏離「系統分析與修改建議」，變成重新設計、演算法或領域專業的專題。期末要做的事很單純，就是把流程與資料的修改想清楚、寫清楚；這部分沒做好，其他做得再多也不會比較高分：

| 不要做 | 為什麼 |
|---|---|
| 把系統整個重新設計 | 期末是依提案書修改既有系統，提案書沒有碰到的部分維持原樣 |
| 最佳化排程、需求預測、自動補貨演算法 | 演算法本身會吃掉整份報告，而課程要評的是分析與修改建議 |
| 影像辨識、AI 自動判定 | 那是另一個領域，而且你無法在報告裡說明它怎麼運作 |
| 複雜成本分析、財務模型 | 效益評估只要求列出指標、修改前的估計值與修改後的目標值 |
| 與 ERP、MES 全面整合 | 系統在本機端執行，提案書沒有要求的介接一律界外 |
| 接感測器、RFID、PLC 等硬體訊號 | 五題都假設資料由人工登記。要接硬體的一律界外 |
