# 工單派工與現場報工系統

> **領域**：生產管理｜**難度**：進階｜**這一題真正要想的問題**：多人同時報工時，數量上限的檢核會失效
>
> 五題共通的名詞見本資料夾的[期末設計題目說明](README.md)〈五〉。
>
> **這是五題中最難的一題**，適合期中做得紮實、分工穩定的組別。難的地方不在功能多，而在有一個問題你無法完全解決、只能說明它。

---

## 一、先看懂這件事在說什麼

### 1.1 一個你已經懂的類比

餐廳的點單。客人點了一份炒飯，廚房收到一張單，做好了就把單子勾掉。

工廠的**工單**就是「做某個產品幾個」的生產指令，作業員做完一批之後回報做了幾個、花多久，那就是**報工**。

**但工廠跟餐廳有一個根本的差別：**

餐廳的一張單是一份炒飯，做完就是做完。工廠的一張工單可能是「做 5,000 個外殼」，這 5,000 個會分成三天、跨三個班別、由五個作業員陸續做完。**每個人做完一段就報一次工。**

所以一張工單會對應到很多筆報工紀錄，而「這張工單做到幾個了」是把所有報工紀錄加起來的結果。

### 1.2 現場實際長什麼樣

**現在的做法：**

| 步驟 | 現況 |
|---|---|
| 排產 | 生管依訂單交期與產能，排出這週各條線要做什麼 |
| 開工單 | 開出工單：產品、數量、交期、指定哪條產線或哪台機台 |
| 發工單 | **工單印成紙本**，貼在機台旁邊的看板上，或夾在生產批次的箱子上 |
| 生產 | 作業員照工單生產 |
| 報工 | 每個班別結束、或做完一批，在工單背面或另一張報工單上手寫：做了幾個、幾個不良、幾點開始幾點結束 |
| 收單 | 班長下班前收單，隔天早上交給生管 |
| 輸入 | 生管把紙本數字輸入電腦 |

**問題出在四個地方：**

**一、進度不透明。** 生管要到隔天才知道昨天做了多少。客戶下午打電話問「我那批貨做得怎樣了」，生管答不出來。

**二、紙本會掉。** 工單貼在機台旁邊三天，會被油污弄髒、被風吹走、被當成廢紙丟掉。

**三、報工超量沒人擋。** 工單 5,000 個，三個人分別報 2,000、2,000、1,500，加起來 5,500——紙本時代沒有人會去加總，這個錯誤要到月底盤點才發現。

**四、工時失真。** 「幾點到幾點」是下班前憑印象補寫的，中間換線、待料、休息的時間都算進去了。

### 1.3 名詞解釋

| 名詞 | 意思 |
|---|---|
| 工單（製造命令，MO，Manufacturing Order） | 「生產某產品、多少數量、什麼時候要完成」的生產指令。工廠生產的最小管理單位 |
| 生管（生產管理人員） | 負責排產、開工單、追進度的人。**不是現場作業員** |
| 派工 | 決定這張工單由哪條產線、哪台機台、哪一班來做 |
| 報工（生產回報） | 作業員回報「我做了幾個、花多久」。**本題的核心動作** |
| 良品數 | 做出來合格的數量 |
| 不良數 | 做出來不合格的數量。要記原因分類，否則管理上沒用 |
| 產出數量 | 良品數加不良數，也就是實際做了幾個 |
| 工時 | 人花的時間 |
| 機時 | 機器運轉的時間。**兩者不一樣**：一個人看三台機，工時 8 小時但機時 24 小時 |
| 工序（站別） | 一個產品要經過的加工步驟，例如沖壓 → 焊接 → 烤漆 → 組裝。**本題可以簡化為單工序** |
| 在製品（WIP，Work In Process） | 已經開始做、還沒做完的東西 |
| 交期 | 客戶要求交貨的日期 |
| 生產進度 | 已報工數量除以工單數量 |
| 未足量結案 | 工單 5,000 個，只做出 4,800 個就結案。剩下的 200 個不補做 |
| 製造執行系統（MES，Manufacturing Execution System） | 工廠管理生產執行的資訊系統。**本題設計的就是它的一小部分** |

**「工時」與「機時」的差別要先弄清楚**，因為它會影響你的資料設計。一個作業員同時顧三台機台，八小時的工時對應二十四小時的機時。你的報工紀錄要記哪一個？記兩個？這個決定會改變後續所有的效率計算。

## 二、為什麼需要一套系統

### 2.1 現在的做法有什麼問題

| 問題 | 具體情況 |
|---|---|
| 進度隔天才知道 | 生管無法即時回答客戶的進度詢問 |
| 紙本遺失 | 工單在現場放三天，弄髒、弄丟、看不清 |
| 報工超量無人擋 | 累計數量超過工單數量，要到盤點才發現 |
| 重複輸入 | 現場手寫一次，生管再輸入電腦一次，兩次都可能出錯 |
| 工時失真 | 下班前憑印象補寫，中間的停頓都算進去了 |
| 不良原因無紀錄 | 只記「不良 30 個」，不知道為什麼不良，改善無從下手 |
| 跨班歸屬混亂 | 晚班 23:00 到隔天 07:00 的產出，算前一天還是後一天 |

### 2.2 系統要解決哪幾件事

1. 作業員在現場直接報工，不必手寫再轉輸入。
2. 生管隨時看得到每張工單的進度。
3. 報工數量超過工單數量時，系統擋下來。
4. 不良品要選原因分類，事後統計得出來。
5. 工時與機時分開記錄。
6. 跨班別、跨日的產出歸屬有明確規則。

## 三、誰會用這套系統

| 角色 | 現場的實際身分 | 在這套系統裡做什麼 | 多久用一次 | 最在意什麼 |
|---|---|---|---|---|
| 生管人員 | 生產管理課的排產人員 | 開立工單、派工、看進度、處理異常（超量、未足量結案） | 每天多次 | 進度要準；異常要看得出來 |
| 現場作業員 | 產線作業員、機台操作員 | 報工 | 每班一到數次 | **報工要非常快。** 他站在機台旁邊，戴手套，交班前趕著填 |
| 生產主管 | 生產課長、線長 | 看各線進度、核准未足量結案、看不良統計 | 每天一次 | 交期會不會延誤；哪條線效率有問題 |

**作業員這一欄的「最在意」是這一題的關鍵。** 他戴著手套、站在吵雜的現場、交班前只剩三分鐘。如果報工畫面要填十個欄位、要用下拉選單捲很久，**他就會回去用紙本**——然後這整套系統就白做了。

期末第 6 項要求考量「手套、掃碼槍、光線、噪音、螢幕尺寸、網路品質」，**這一題是五題中最需要認真處理這一段的**。工單號碼要不要用掃碼槍掃？數字鍵盤要多大？這些問題有具體答案。

## 四、要管哪些東西

以下用白話列出，**怎麼拆成資料表、每張表有哪些欄位是你的工作，這裡不給。**

**關於工單**

- 做什麼產品（品號、品名）
- 要做幾個
- 交期
- 指定哪條產線或哪台機台
- 誰開的、什麼時候開的
- 目前處理到哪裡

**關於每一次報工**

- 對應哪一張工單
- 誰報的、什麼時候報的
- 哪一個班別
- 做了幾個良品、幾個不良
- 不良的原因分類
- 開始時間與結束時間（或直接填工時）
- 用了哪台機台

**關於基礎資料**

- 有哪些產品
- 有哪些產線與機台
- 有哪些班別，各自的起訖時間
- 有哪些不良原因分類

**注意班別這一組資料。** 「晚班是 23:00 到 07:00」這件事必須是資料，因為它會被用來判斷一筆報工屬於哪個班別、屬於哪一天。寫死在程式裡，換班制度改變時就要改程式。

## 五、一張單子的一生

```text
開立（生管建立工單）
  → 待派工
  → 已派工（指定產線或機台）
  → 生產中（開始有報工紀錄）
  → 完工（累計數量達到工單數量）
  → 結案
```

**例外會發生在這幾個地方，設計時都要有答案：**

| 環節 | 例外情況 | 你要決定什麼 |
|---|---|---|
| 報工 | 累計數量加起來超過工單數量 | 硬性擋下？允許超量但標示？允許但要主管核准？**見第六節** |
| 報工 | 兩個人同時報工，各自檢查都通過，加起來超量 | **見第六節，這是本題的核心** |
| 報工 | 數字填錯了要更正 | 允許改嗎？改了累計進度怎麼跟著變？誰有權限改？ |
| 生產中 | 做到 4,800 個，剩 200 個做不出來（材料不足、良率不佳） | 允許「未足量結案」嗎？誰核准？工單數量還算是承諾嗎？ |
| 生產中 | 客戶取消訂單，工單要中止，但已經做了 3,000 個 | 這 3,000 個怎麼處理？工單狀態變成什麼？ |
| 報工 | 晚班 23:00 開始、隔天 07:00 結束 | 這筆產出算哪一天？工時算哪一天？ |
| 生產中 | 這張工單其實還沒開始做，但有人誤報工了 | 報工紀錄能刪嗎？刪了要不要留痕跡？ |

**「未足量結案」與「跨日報工」這兩條，多數組別會漏掉。** 前者會讓工單永遠掛在「生產中」，後者會讓每天的產量統計對不上——兩者都不是罕見狀況。

## 六、這一題的設計難點

### 6.1 主要難點：數量上限的檢核擋不住同時報工

這是本題被列為進階的原因。**先把情境看懂。**

一張工單要做 5,000 個。目前累計已報 4,980 個，也就是還剩 20 個。

作業員甲和作業員乙在同一秒鐘各報 15 個。系統的檢查邏輯是「已報 + 這次要報 ≤ 工單數量」。

**兩人各自的檢查過程：**

| | 甲 | 乙 |
|---|---|---|
| 讀出目前累計 | 4,980 | 4,980（同一個數字，因為甲還沒寫進去） |
| 算一下 | 4,980 + 15 = 4,995 | 4,980 + 15 = 4,995 |
| 判斷 | 4,995 ≤ 5,000，**通過** | 4,995 ≤ 5,000，**通過** |
| 寫入 | 寫進 15 個 | 寫進 15 個 |

**兩人都通過了檢查，但實際累計變成 5,010 個——超量了。**

問題的根源很單純：**兩個請求各自讀到同一個舊數字**。甲讀完之後、寫進去之前的那個瞬間，乙也讀了，讀到的還是舊的 4,980。

### 6.2 本課程對這一題的要求

**你不需要解決這個問題。** 資料庫層的鎖定與交易控制超出本課程範圍，那是軟體工程的內容。

**你需要做到兩件事：**

**一、在第 7 項的風險分析裡指出它存在，並說明它為什麼發生。** 不能只寫「可能會超量」，要寫出上面那張表的推演過程——兩個請求讀到同一個舊值。**這個推演寫得出來，就代表你真的懂了。**

**二、判斷它多久會發生一次、後果多嚴重，據此決定這次要不要處理。** 這是可行性判斷，不是技術判斷：

| 要問的 | 這一題的情況 |
|---|---|
| 多久發生一次 | 只在「兩人在同一瞬間報同一張工單」時發生。一天幾次？取決於一張工單有幾個人同時做 |
| 後果多嚴重 | 累計數量比工單多幾個。會不會影響出貨？會不會影響物料帳？ |
| 有沒有其他把關 | 出貨前會不會盤點？包裝時會不會數？如果有，這個錯誤會被下游攔下 |
| 這次要不要處理 | 依上述判斷。**不處理也可以，但要說明理由**，並列為殘餘風險 |

**「知道有問題、評估過、決定這次不處理」與「不知道有問題」是完全不同的兩件事。** 前者是工程判斷，後者是疏漏。這一題就是在教這個區別。

### 6.3 第二個難點：累計數量該存還是該算

跟物料領退料那一題同一個結構的問題，但這裡多一層。

| 做法 | 好處 | 代價 |
|---|---|---|
| 存成工單上的累計欄位 | 查進度快；上限檢核只要讀一個數字 | 報工紀錄被更正或刪除時，累計欄位要跟著改 |
| 每次由報工紀錄加總算出來 | 永遠正確 | 每次查進度都要加總；工單多時清單會慢 |

**多的那一層是這個：報工紀錄可以被更正。**

作業員把 150 打成 15，隔天發現要改。這時：

- 選「存累計欄位」→ 改報工紀錄時，累計欄位必須同步修正。**誰負責？漏了怎麼發現？**
- 選「每次算」→ 改了自然正確，**但已經根據錯誤進度做出的決定（例如生管以為快做完了，排了下一張工單）已經發生了**

第二點值得寫進報告：**資料改對了，但基於錯資料做的決定不會自動還原。** 這是資訊系統的限制，不是設計缺陷，但要指出來。

### 6.4 第三個難點：未足量結案要不要允許

工單 5,000 個，做到 4,800 個做不下去了（材料用完、良率太差、客戶改單）。

| 做法 | 代價 |
|---|---|
| 不允許，一定要做滿才能結案 | 這張工單會永遠掛在「生產中」。三個月後，未結案清單上有一堆殭屍工單 |
| 允許，任何人都能結案 | 工單數量就不是承諾了，任何人都能宣告「做不下去」 |
| 允許，但要生產主管核准並填原因 | 較合理，但主管會多一件事要做；而且「原因」要不要分類？ |

第三種做法還會引出一個資料問題：**未足量結案的工單，它的「完成率」是 96% 還是 100%？** 統計月產量時，這張工單算做完了嗎？這個定義會直接改變管理報表的數字。

### 6.5 這一題會逼你回答什麼

**三件事，一件比一件深：**

1. **有些問題你解決不了，但必須說得出它為什麼存在。** 這是 6.1。
2. **同一份設計裡，哪些數字該存、哪些該算。** 這是 6.3。
3. **資料是為了管理決策而存在的，資料定義會改變決策。** 這是 6.4——「未足量結案算不算做完」不是技術問題，是你替管理者定義了一個指標。

**所有取捨都由你決定，理由與代價寫進第 8 項的設計決策紀錄；6.1 那條寫進第 7 項的風險分析。**

## 七、容易走偏的方向

| 走偏的做法 | 為什麼不對 |
|---|---|
| **做成自動排程系統**（自動決定工單先後順序、自動派給機台） | **這是本題最常見也最嚴重的走偏。** 排程演算法會吃掉整份報告，系統設計反而寫不出來。本題只做工單的登錄、人工派工與報工，排產順序由生管決定 |
| 設計成一張工單只報一次工 | 難點全部消失。一張工單多人多次報工是這一題的前提 |
| 不良只記一個數字，不記原因 | 管理上沒有用。不良原因分類是這套系統的主要價值之一 |
| 想接製造執行系統或可程式邏輯控制器自動取數 | 資料交換可以設計（例如讀取企業資源規劃系統的工單），但**不要做設備連線**，那超出範圍 |
| 工時直接用「結束時間減開始時間」 | 中間的換線、待料、休息、開會算不算？不回答這個問題，工時數字沒有意義 |
| 忽略跨日與跨班的歸屬 | 每天的產量統計會對不上，而這是這套系統最基本的輸出 |
| 把工序做成完整的多站別流程（沖壓 → 焊接 → 烤漆 → 組裝各自報工） | 資料模型會跳一級（在製品要在站別之間流動）。**建議簡化為單工序**，有餘力再列為可選項目 |
| 把進度百分比存成一個欄位 | 它是算出來的（已報數量除以工單數量），存起來就要維護 |

## 九、第一週建議做什麼

1. **Google「工單 範本」與「報工單 範本」**，各找一份，把欄位抄下來對照。你會發現工單的欄位跟報工單的欄位幾乎不重疊——這就是主檔與明細的分工。
2. **訪問一位實習過生產線的同學。** 問「你們怎麼報工」，然後追問「一張工單幾個人做」「有沒有報錯過、怎麼改」。這十分鐘會決定你這一題做得深不深。
3. **把 6.1 那個並行的例子用自己的話重寫一次。** 不要照抄那張表，用自己的話從頭推一遍。**寫得出來才代表懂了**，而這一段是第 7 項風險分析的核心材料。
4. **決定 6.3 與 6.4 兩個取捨**，各寫三句理由。
5. **想清楚報工畫面要幾個欄位。** 作業員戴手套、交班前只剩三分鐘。你能砍到幾個欄位？砍掉的資訊從哪裡來？

第 3 步與第 5 步是這一題最能拉開差距的地方。第 3 步證明你懂那個問題，第 5 步證明你把使用者當成真人而不是資料輸入機。
