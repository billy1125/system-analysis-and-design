# 設備報修與維修派工系統

> **領域**：設備維護｜**難度**：標準｜**這一題真正要想的問題**：完修不等於結案，報修人不驗收就會卡單
>
> 五題共通的名詞見本資料夾的[期末設計題目說明](README.md)〈五〉。

---

## 一、先看懂這件事在說什麼

### 1.1 一個你已經懂的類比

宿舍的冷氣壞了。你上學校的報修系統填一張單子，寫下房號跟故障情況。工務組收到後派人來看，換了電容，修好了。走之前請你確認冷氣有在吹，你簽個名，這張單子就結案了。

**工廠的設備報修就是同一件事，只是三件事不一樣：**

| | 宿舍冷氣 | 工廠設備 |
|---|---|---|
| 壞掉的代價 | 你熱一個晚上 | 一條產線停一小時，少產幾百件，可能延誤客戶交期 |
| 急迫性 | 隔天修也可以 | 分鐘計算，會有人一直催 |
| 為什麼要留紀錄 | 沒特別需要 | 要算平均修復時間、要找出常故障的機台、要決定該不該換新設備 |

### 1.2 現場實際長什麼樣

作業員在生產中發現機台不對——異音、精度跑掉、報警燈亮、或者完全不動。

**現在的做法：**

| 步驟 | 現況 |
|---|---|
| 通知 | 打電話給維修室，或在通訊軟體群組喊一聲，或直接跑去維修室找人 |
| 受理 | 維修人員看到了、口頭答應 |
| 到場 | 有空就來，忙的時候排隊，但排在第幾個沒有人知道 |
| 判斷與維修 | 現場檢查、拆開看、換零件、調整 |
| 完成 | 試機正常，跟作業員說「好了」，人就走了 |
| 紀錄 | 有的廠會在一本簿子上補登，有的完全沒有 |

**問題在月底。** 主管想知道這個月設備總共停了多少小時、哪一台最會壞、維修人員的工作量分配是否合理——這些全部答不出來，只能靠回想。

更麻煩的是：同一台機台這半年壞了七次，但因為沒有紀錄，沒人察覺這件事。這台機台其實已經該大修或換掉了。

### 1.3 名詞解釋

| 名詞 | 意思 |
|---|---|
| 報修（通報） | 發現設備異常時通知維修單位 |
| 受理 | 維修單位確認收到這件報修，開始處理 |
| 派工 | 指定由哪一位維修技師負責 |
| 完修（修復完成） | 維修技師認為問題已解決，設備可以恢復生產 |
| 驗收 | 由報修人確認設備真的正常了。**完修是維修方說的，驗收是使用方說的** |
| 故障類別 | 故障原因的分類，例如機械類、電氣類、氣壓類、程式類、操作不當 |
| 停機時間 | 設備因為這次故障無法生產的時間長度 |
| 平均修復時間（MTTR，Mean Time To Repair） | 每次故障平均花多久修好。**這是這套系統最主要的效益指標** |
| 平均故障間隔（MTBF，Mean Time Between Failures） | 兩次故障之間平均隔多久。數字越大代表設備越可靠 |
| 備品（備料） | 維修用的零件庫存，例如馬達、軸承、感測器 |
| 故障維修 | 壞了才修，也叫事後保養 |
| 預防保養 | 還沒壞就定期保養，避免故障。**本題只做故障維修**，預防保養是另一個題目 |
| 試機 | 修完後開機測試，確認正常 |

**「完修」與「驗收」的差別是本題的核心**，一定要先分清楚。維修技師說「修好了」是完修；報修的作業員實際生產一段時間確認沒問題，那才是驗收。兩者中間有落差，而那個落差就是這一題的設計難點。

## 二、為什麼需要一套系統

### 2.1 現在的做法有什麼問題

| 問題 | 具體情況 |
|---|---|
| 叫修靠喊 | 誰報的、什麼時候報的沒有紀錄。兩個人報同一台，維修來了兩次 |
| 等待時間不透明 | 作業員不知道還要等多久，只能一直打電話催 |
| 反覆故障看不出來 | 同一台半年壞七次，沒有資料可以證明 |
| 維修工時無紀錄 | 算不出維修人員的負荷，也算不出停機成本 |
| 備品用量不明 | 換了什麼零件沒登記，倉庫的備品庫存永遠不準 |
| 指標算不出來 | 平均修復時間、平均故障間隔這兩個最基本的設備管理指標，都拿不到數字 |
| 修完就沒下文 | 沒有人確認真的修好了。三天後又壞，算新故障還是同一件事？ |

### 2.2 系統要解決哪幾件事

1. 報修有紀錄，誰報的、什麼時候報的、目前處理到哪裡都查得到。
2. 作業員看得到自己報的單子現在什麼狀態。
3. 維修單位看得到待處理清單，可以決定先修哪一台。
4. 每次維修的處理內容、工時與用掉的備品都留下紀錄。
5. 算得出每台設備的故障次數與平均修復時間。
6. 修完要由報修人確認，不是維修方單方面說結束。

## 三、誰會用這套系統

| 角色 | 現場的實際身分 | 在這套系統裡做什麼 | 多久用一次 | 最在意什麼 |
|---|---|---|---|---|
| 報修人員 | 現場作業員、產線班長 | 報修、查自己報的單子進度、驗收 | 每週一兩次 | 報修要快（機台停著，沒空慢慢填表）；要知道還要等多久 |
| 維修技師 | 設備維修人員 | 看待處理清單、受理、登錄處理內容與工時、回報完修 | 每天多次 | 不要一直被電話催；登錄不要太繁瑣 |
| 設備主管 | 設備課長、廠務經理 | 派工、看未結案清單、看設備故障統計 | 每天一次 | 不要有停很久還沒修的設備；要有數字可以向上報告 |

**報修人員是在機台旁邊、機台停著的狀況下操作的。** 他手上可能還有一堆事，設備正在停產，主管在後面看。**這時候要他填十五個欄位是不現實的。** 這一題的介面設計要在「資料完整」與「報修要快」之間取捨，是期末第 6 項很好的材料。

## 四、要管哪些東西

以下用白話列出，**怎麼拆成資料表、每張表有哪些欄位是你的工作，這裡不給。**

**關於設備**

- 有哪些設備（編號、名稱、型號、廠牌）
- 放在哪一條產線、哪個區域
- 目前狀態（正常生產、故障停機、維修中、停用）

**關於每一次報修**

- 哪一台設備
- 誰報的、什麼時候報的
- 故障情況的描述（可能還有照片）
- 設備是否已經停機（有些異常還可以勉強生產）
- 急迫程度

**關於維修處理**

- 誰受理的、什麼時候受理
- 派給誰
- 什麼時候到場、什麼時候完成
- 故障原因與類別
- 做了什麼處理
- 換了哪些備品、各幾個
- 花了多少工時

**關於驗收**

- 誰驗收的、什麼時候
- 通過或不通過
- 不通過的原因

**注意「一次報修可能有多次維修處理」。** 技師來看了一次，發現要等零件，先回去；零件到了再來一次；修完發現還是不行，第三次來。這三次都是同一張報修單下的處理紀錄。這是本題主檔與明細的分界。

## 五、一張單子的一生

```text
報修（作業員開單）
  → 待受理
  → 已受理（維修單位確認收到）
  → 已派工（指定技師）
  → 維修中
  → 完修（技師回報處理完成）
  → 待驗收
  → 驗收通過 → 結案（終點）
  → 驗收不通過 → 退回「維修中」
```

**例外會發生在這幾個地方，設計時都要有答案：**

| 環節 | 例外情況 | 你要決定什麼 |
|---|---|---|
| 待驗收 | 報修人下班、換班、離職，沒有人來驗收 | **這是本題的核心難點**，見第六節 |
| 判斷後 | 檢查發現不是故障，是作業員操作錯誤 | 要有一個「非故障結案」的出口嗎？這種單子算不算故障次數？ |
| 維修中 | 需要等外部廠商或等備品，可能等三天 | 要不要有「暫停」狀態？**這三天算在修復時間裡嗎？** |
| 報修 | 同一台設備在維修中又被報修一次 | 合併成同一張單，還是兩張各自處理？ |
| 維修中 | 修不好，要送外廠或報廢設備 | 這張報修單怎麼結束？ |
| 完修 | 修完三天後同一個問題又出現 | 算新的報修，還是原單重開？（會影響故障次數的統計） |

**「暫停等料」與「同問題再次故障」這兩條，會直接改變指標的數字。** 等料的三天算不算修復時間，平均修復時間可以差好幾倍；三天後再壞算新故障還是原單，故障次數的統計完全不同。這些不是技術問題，是**你替管理者定義指標**——這一點在報告裡值得寫。

## 六、這一題的設計難點

### 6.1 問題在哪

設計上你會很自然地加入「驗收」這個環節，理由充分：**只有使用設備的人才知道問題真的解決了沒有**。維修技師試機十分鐘正常，不代表連續生產八小時都正常。

**但驗收會卡單。**

具體情境：早班的作業員甲在上午 9 點報修，維修在中午修好，回報完修。甲下午 4 點下班了。這張單子停在「待驗收」，然後停在那裡一個月。

這不是罕見狀況，而是**每週都會發生**。原因很單純：機台已經在跑了，對甲來說事情已經結束，他沒有動機去點那顆驗收按鈕。

### 6.2 三種處理方式，各自的代價

**做法 A：設自動結案期限**

完修後 3 天內無人提出異議，系統自動結案。

| | |
|---|---|
| 好處 | 簡單，不需要多加角色或權限，卡單問題直接消失 |
| 代價 | **可能把沒真正修好的單子關掉。** 甲下週回來發現還是有問題，但單子已經自動結案了，他只能重新報修——於是統計上變成兩次故障 |
| 要多決定 | 幾天算合理？3 天遇到連假就變成沒人看過就結案 |

**做法 B：允許同班別或同單位的任何人代為驗收**

不限原報修人，同產線的人都可以驗收。

| | |
|---|---|
| 好處 | 不卡單，而且驗收的人確實在現場、確實知道機台狀況 |
| 代價 | **驗收失去「原報修人確認」的意義。** 代驗的人可能不知道原本的故障情況是什麼，看機台在轉就簽了 |
| 要多決定 | 「同班別」「同單位」的範圍怎麼定？這需要組織或產線的歸屬資料 |

**做法 C：主管可強制結案**

單子卡住時，由設備主管判斷後強制結案。

| | |
|---|---|
| 好處 | 保留了把關，而且是由有判斷力的人決定 |
| 代價 | **主管變成瓶頸。** 每週要處理十幾張卡住的單子，主管會覺得這系統很煩 |
| 要多決定 | 主管憑什麼判斷？他也不在現場。強制結案要不要留下原因？ |

### 6.3 選完之後還有一個問題

**已經卡住的舊單怎麼辦？**

假設你選了做法 A（3 天自動結案），但系統上線時已經有 40 張卡在「待驗收」超過三個月的舊單。

| 做法 | 代價 |
|---|---|
| 新規則只對上線後的新單生效 | 那 40 張永遠卡著，未結案清單上永遠有 40 筆雜訊 |
| 回頭套用，全部自動結案 | 一次結掉 40 張，但其中可能真的有沒修好的 |
| 由主管逐張處理 | 最正確，但要花時間，而且沒有人想做 |

**這一題叫做資料轉換或歷史資料處理**，在真實專案中每次都會遇到，而在課堂報告中幾乎每組都會漏掉。能主動寫進第 8 項的待解問題清單，會明顯拉開差距。

### 6.4 這一題會逼你回答什麼

**一個把關機制，如果依賴某個人主動操作，而那個人沒有動機操作，這個機制就會失效。**

設計時不能只想「應該由誰確認」，還要想「他為什麼會去確認、不確認會怎樣」。這是流程設計與純資料設計最大的差別，也是這一題最值得學的東西。

**要選 A、B、C 還是別的做法，你自己決定，理由與代價寫進第 8 項的設計決策紀錄。** 三個選擇在真實系統裡都有人用。

## 七、容易走偏的方向

| 走偏的做法 | 為什麼不對 |
|---|---|
| 把驗收拿掉，因為它很麻煩 | **這一題的難點就消失了。** 設計深度會被扣分，而且訪談時「你怎麼知道真的修好了」答不出來 |
| 只做「報修 → 完修」兩個狀態 | 活動圖沒有分岔，狀態機圖沒東西可畫，第 3 項會很空 |
| 想做設備連線自動偵測異常並自動報修 | 超出範圍，技術可行性也評估不了。本題是人工報修 |
| 把備品扣帳做成完整的倉儲管理 | 範圍會爆掉。本題只需要記「這次維修用了哪些備品、各幾個」，不做庫存管理 |
| 把平均修復時間存成一個欄位 | 它是算出來的。而且原始資料被更正後，存起來的數字就對不上了 |
| 只記「開始時間」與「結束時間」就算出工時 | 中間的等料、休息、換班算不算？這個問題不回答，工時數字沒有意義 |
| 把「非故障」（操作錯誤）當成故障處理 | 統計會被污染。這種單子要能被排除在故障次數之外 |
| 做成完整的預防保養排程系統 | 那是另一個題目。本題只做故障維修 |

## 九、第一週建議做什麼

1. **把學校的報修系統走一遍。** 填一張測試單（或看填單畫面），記下它問了哪些欄位、有沒有讓你看進度、修完有沒有要你確認。這是這一題最直接的參考。
2. **訪問一位實習過的同學，問三個問題**：機台壞了怎麼叫修、從報修到修好通常多久、修完有沒有人要你確認。十分鐘就夠。
3. **畫一張報修單的一生**，把第五節例外表裡你答不出來的問題圈出來。
4. **決定第六節的卡單怎麼處理**，並回答 6.3 那個問題（舊單怎麼辦）。寫成五句話。

第 4 步的第二半（舊單怎麼辦）多數組別會漏掉。**主動寫出來，第 8 項的待解問題清單就會有一條別人沒有的。**
