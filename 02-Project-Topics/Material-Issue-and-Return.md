# 物料領退料管理系統

> **領域**：物料與倉儲｜**難度**：標準｜**這一題真正要想的問題**：已領量該存成欄位，還是每次算出來
>
> 五題共通的名詞見本資料夾的[期末設計題目說明](README.md)〈五〉。

---

## 一、先看懂這件事在說什麼

### 1.1 一個你已經懂的類比

實驗課要做實驗，你填一張單子去實驗室領耗材：試管 5 支、燒杯 2 個。助教找出東西、點給你、你簽名。實驗做完，試管剩 2 支沒用到，你拿回去還給助教。

**工廠的領退料就是同一件事**，只是三個地方不一樣：

| | 實驗室耗材 | 工廠物料 |
|---|---|---|
| 數量 | 5 支 | 3,000 個，或 250 公斤 |
| 種類 | 十幾種 | 幾千種，每種有自己的編號 |
| 記錯的後果 | 助教皺一下眉 | 帳面庫存跟實際差幾萬個，該叫料的沒叫，生產線停下來等料 |

### 1.2 現場實際長什麼樣

生產之前，現場要向倉庫領出這批產品需要的原料與零件。

**現在的做法：**

| 步驟 | 現況 |
|---|---|
| 開單 | 現場班長手寫一張三聯式領料單：料號、品名、需求數量、工單號碼 |
| 核准 | 生產主管簽名（有些廠省略這一步） |
| 找料 | 倉管拿著單子去庫位找東西 |
| 發料 | 點數、簽名，一聯留倉庫、一聯給現場、一聯給會計 |
| 輸入電腦 | **通常是月底才一起輸入**，有的廠一週一次 |
| 退料 | 生產結束，剩下的料拿回倉庫，再填一張退料單 |

**問題出在三個地方：**

**一、帳面跟實際差很多。** 領料單月底才輸入，這代表月中的任何時候，電腦上的庫存數字都是錯的。生管看著電腦說「這料還有 5,000 個」，實際上倉庫早就空了。

**二、現場暗庫。** 領出來沒用完、也沒退回去的料，堆在產線旁邊的角落。帳上顯示「已發出」，實際上東西還在，但沒有人知道有多少。下次要用又去領新的，於是同一種料在廠裡三個地方各有一堆。

**三、部分領料算不清。** 一張單子申請 1,000 個，倉庫當時只有 600 個，先發 600。剩下的 400 個什麼時候補發？補發了沒有？手寫單子上加註一行「已發 600」，然後第二次發料時再加一行——三次之後就沒人看得懂了。

### 1.3 名詞解釋

| 名詞 | 意思 |
|---|---|
| 物料 | 生產要用的東西，包含原料、零件、包材、耗材 |
| 料號 | 每一種物料的唯一編號。**同一種東西不同規格是不同料號**，例如 M3×8 螺絲與 M3×10 螺絲是兩個料號 |
| 領料 | 現場向倉庫申請並取得物料 |
| 發料 | 倉庫把物料交給現場。**領料是現場的動作，發料是倉庫的動作**，兩者是同一件事的兩面 |
| 退料 | 領出去沒用完的物料退回倉庫 |
| 領料單 | 記錄一次領料需求的單據 |
| 庫位 | 物料在倉庫中的存放位置，例如 `A-03-2`（A 區第 3 排第 2 層） |
| 帳面庫存 | 系統或帳冊上記錄的數量 |
| 實際庫存 | 倉庫裡真的有幾個 |
| 安全庫存 | 為了避免缺料而保留的最低庫存量。低於這個數就該叫料 |
| 工單 | 「生產某產品、多少數量」的生產指令。領料通常是為了某一張工單 |
| 呆料 | 長期沒有用到的物料，佔著倉庫空間與資金 |
| 暗庫 | 帳上已經發出、實際還留在現場沒用掉的物料。**帳實不符最主要的來源之一** |
| 計量單位 | 這個料號用什麼單位計算，常見 PCS（個）、KG（公斤）、M（公尺）、箱、卷 |
| 部分領料 | 一張領料單分成兩次以上發料。**這是常態，不是例外** |

**「計量單位」是這一題的隱藏陷阱。** 同一個料號可能有「箱」與「個」兩種說法，一箱 24 個。現場寫「領 2 箱」，倉庫發了 48 個。系統要存 2 還是 48？兩者混用一次，庫存就永久錯下去。設計時務必決定清楚。

## 二、為什麼需要一套系統

### 2.1 現在的做法有什麼問題

| 問題 | 具體情況 |
|---|---|
| 帳實不符 | 月底才輸入，月中的庫存數字全部不可信 |
| 現場暗庫 | 領出去沒退的料堆在現場，帳上找不到 |
| 部分領料算不清 | 一張單分三次發，第三次發多少要用心算 |
| 缺料到現場才發現 | 倉管去找料才知道沒有，這時生產已經要開始了 |
| 退料無人管 | 退料單常常沒填，料就留在現場 |
| 追不出去向 | 客戶抱怨某批產品有問題，想查它用了哪一批料，查不到 |
| 單位混用 | 箱與個混寫，庫存數字出現無法解釋的差異 |

### 2.2 系統要解決哪幾件事

1. 領料與發料當場登錄，庫存數字隨時是對的。
2. 一張領料單分幾次發、目前還差多少，一眼看得出來。
3. 退料有紀錄，領出去沒退的料查得出來。
4. 開單時就知道庫存夠不夠，不必等倉管去找才發現缺料。
5. 每一筆物料的進出都有經手人與時間。

## 三、誰會用這套系統

| 角色 | 現場的實際身分 | 在這套系統裡做什麼 | 多久用一次 | 最在意什麼 |
|---|---|---|---|---|
| 領料人員 | 產線班長、現場作業員 | 開領料單、查發料狀況、辦退料 | 每天一兩次 | 開單要快；要能事先知道倉庫有沒有貨 |
| 倉管 | 倉庫管理員 | 看待發料清單、登錄實發數量、收退料 | 每天多次 | 登錄要快，一次可能要處理十幾張單；不要因為系統慢而排隊 |
| 生產主管 | 生產課長 | 核准領料單、看領用異常（領很多沒退） | 每天一次 | 不要有人超領；異常要看得出來 |

**倉管是使用頻率最高的角色**，一天可能登錄幾十筆。他站在倉庫裡，手上拿著料、推著推車。**這個角色的介面如果慢，整套系統就會被繞過**——他會回去用紙本，晚上再補登，於是帳實不符的問題原封不動。這是期末第 6 項〈介面原型〉最該處理的重點。

## 四、要管哪些東西

以下用白話列出，**怎麼拆成資料表、每張表有哪些欄位是你的工作，這裡不給。**

**關於物料**

- 有哪些料號、品名、規格
- 計量單位
- 放在哪個庫位
- 目前庫存數量
- 安全庫存量

**關於每一張領料單**

- 為了哪一張工單領的（或是什麼用途）
- 誰開的、什麼時候
- 誰核准的
- 目前處理到哪裡

**關於領料單上的每一個項目**

- 哪一個料號
- 申請多少
- 實際發了多少
- 退回多少

**關於每一次發料與退料**

- 對應哪一張領料單的哪一個項目
- 這一次發（或退）了多少
- 誰經手的、什麼時候

**這裡有一個關鍵的結構問題。** 「實際發了多少」如果一張單只發一次，寫在領料單的項目上就好。但**部分領料是常態**——一個項目可能分三次發完。那麼「每一次發料」就必須是獨立的紀錄，而「實際發了多少」變成那三次的總和。

**這正是第六節的難點所在。** 這一段先看懂結構的問題在哪，答案留到第六節。

## 五、一張單子的一生

```text
開立（現場填料號與需求量）
  → 待核准
  → 已核准
  → 待發料
  → 部分發料（發了一部分，還有未發完的）
  → 全數發料
  → 結案
```

退料可以發生在「部分發料」之後的任何時間點，甚至結案之後。

**例外會發生在這幾個地方，設計時都要有答案：**

| 環節 | 例外情況 | 你要決定什麼 |
|---|---|---|
| 開立 | 庫存不足，只能發一部分 | **這是常態。** 剩下的怎麼追？單子停在「部分發料」等補發，還是關掉重開一張？ |
| 開立 | 料號打錯了，領到不對的東西 | 已核准後還能不能改？改了要不要重新核准？ |
| 已核准 | 現場說不用了 | 要有取消的出口。已經發了一部分的能不能取消？ |
| 退料 | 退回來的料已經拆封、污損、或混料了 | 這能算入庫嗎？還是要另立一個「待判定」的狀態？ |
| 退料 | 現場說不出這批料是哪一張單領的 | **見第六節。** 退料要不要強制對應到原領料單？ |
| 結案 | 領了三個月，沒發完也沒退也沒結案 | 要不要自動結案？未發完的部分怎麼處理？ |
| 單位 | 現場寫「2 箱」，倉庫要發 48 個 | 系統存哪一個數字？誰負責換算？ |

**「庫存不足只能發一部分」這一條不是例外，是常態。** 如果你的設計把它當例外處理，主流程會走不通。第六節就是在處理這件事。

## 六、這一題的設計難點

### 6.1 第一個問題：已領量該存還是該算

情境：一張領料單的某個項目申請 1,000 個。第一次發 600，第二次發 400。

「已領 1,000」這個數字要怎麼來？

**做法 A：存成領料明細上的一個累計欄位**

每次發料時，把該項目的「已發數量」加上去。

| | |
|---|---|
| 好處 | 查詢快。要判斷「這張單發完了沒」，直接比較已發數量與申請數量 |
| 代價 | **某次發料紀錄被更正或刪除時，累計欄位就對不上了，而且沒有人會發現。** 畫面上顯示已發 1,000，實際的發料紀錄加起來只有 940 |
| 要多決定 | 誰負責在更正發料紀錄時同步修正累計欄位？如果漏了，怎麼發現？ |

**做法 B：不存，每次由發料紀錄加總算出來**

| | |
|---|---|
| 好處 | **永遠正確。** 發料紀錄改了，加總自然跟著變 |
| 代價 | 每次開清單都要對每一張單的每一個項目做加總。單子多的時候會慢 |
| 連帶影響 | 「這張單結案了沒」也變成算出來的，不是一個存起來的狀態 |

**這個決定會改變你的資料表結構**，所以要在畫實體關聯圖之前就決定。

### 6.2 第二個問題：退料怎麼記

**做法 A：沖回原領料明細**

退 50 個，就把該項目的已發數量從 1,000 減成 950。

| | |
|---|---|
| 好處 | 帳面數字直接反映淨領用量，最直觀 |
| 代價 | **「這批料曾經領出去過」的事實消失了。** 事後查不出這張單總共經手過多少料，也查不出退料發生在什麼時候 |

**做法 B：另立一筆退料紀錄**

領料紀錄不動，退料是一筆獨立的紀錄。

| | |
|---|---|
| 好處 | 歷史完整。領了多少、退了多少、什麼時候退的都查得到 |
| 代價 | 「淨領用量」變成要算的（發料總和減退料總和）。畫面上要顯示三個數字：申請、已發、已退 |

### 6.3 選了 B 之後還有一個問題

**退料要不要對應到原本的哪一張領料單？**

| 做法 | 好處 | 代價 |
|---|---|---|
| 要對應 | 算得出每一張單的淨領用量，追溯完整 | **現場通常說不出來。** 三張單領的同一個料號混在一起放，退回來的 50 個是哪一張領的？沒人知道 |
| 不對應 | 現場好操作，退料就是「這個料號退 50 個回倉庫」 | 每一張單的淨領用量算不出來，只算得出料號層級的總量 |
| 折衷 | 系統建議一張最可能的單（例如最近一張未結案的），讓現場確認或修改 | 兩邊兼顧，但要多設計一段建議邏輯，而且現場可能一律按確認 |

**這一組取捨是本題最值得寫的部分。** 它不是技術問題，而是**資料完整性與現場可操作性之間的衝突**：要求對應，資料漂亮但現場填不出來（於是現場乾脆不退料，回到暗庫問題）；不要求對應，現場好用但你原本要解決的追溯問題只解決了一半。

### 6.4 這一題會逼你回答什麼

**兩件事：**

一、**同一份設計裡，哪些數字該存、哪些該算。** 這是資料設計最核心的判斷，而這一題把它擺在最明顯的位置。

二、**設計得太嚴謹，使用者會繞過它。** 要求退料必須對應原單，聽起來很嚴謹，實際結果可能是現場乾脆不退料——你的系統反而讓暗庫問題變嚴重。**一個沒有人願意用的正確設計，比一個有點鬆但大家都在用的設計更糟。** 這一點在第 7 項的組織可行性裡值得寫。

**三個取捨都由你決定，理由與代價寫進第 8 項的設計決策紀錄。**

## 七、容易走偏的方向

| 走偏的做法 | 為什麼不對 |
|---|---|
| 做成完整的庫存管理系統 | **範圍會爆掉。** 本題只管領與退，不做進貨、盤點、調撥、報廢。庫存數字只因領退料而變動 |
| 忽略計量單位 | 箱與個混用一次，庫存永久錯下去。這是必須在設計階段就處理的問題 |
| 把「部分領料」當成例外 | 它是常態。當成例外處理，主流程會走不通 |
| 不設核准就直接發料 | 少一個角色，權限設計沒東西可寫，第 2 項與第 3 項都會很薄 |
| 想做安全庫存自動補料建議 | 那是採購系統的功能，超出範圍。本題只需要顯示「低於安全庫存」的提醒 |
| 想做批號追溯（哪一批產品用了哪一批料） | 這會讓資料模型跳一級（要管批號、有效期、先進先出）。有興趣可列為可選項目，不要放進必做範圍 |
| 把庫存數量存在物料主檔上就不管了 | 那要回答：這個數字是誰在什麼時候更新的？跟發料紀錄加起來對不對得上？（同 6.1 的問題） |
| 領料單不連工單 | 那就查不出「這張工單用了多少料」，這套系統最主要的管理價值之一就沒了 |

## 九、第一週建議做什麼

1. **找一張真的領料單。** Google「領料單 範本」有大量實例。把上面每一個欄位抄下來，逐一問：誰填的？填了給誰看？
2. **問一個問題：部分領料常不常發生？** 問實習過的同學，或問老師。答案幾乎一定是「很常」，這會確認你必須把它設計進主流程。
3. **問第二個問題：退料真的會退嗎？** 這個問題的答案會告訴你 6.3 該怎麼選。如果現實中大家都懶得退，那麼「要求退料必須對應原單」就是一個會讓系統失效的設計。
4. **決定 6.1、6.2、6.3 三個取捨**，各寫兩三句理由。

第 3 步最容易被忽略，但它是這一題與現實接得上的關鍵。**設計一個沒有人會用的功能，等於沒設計。**
