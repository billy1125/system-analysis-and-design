# 期中分析範例系統

這個資料夾收錄四套可以實際跑起來的校園情境系統，供期中小組報告（系統分析）分析使用。

## 一、這些系統在回答什麼

期中做的是系統分析，分析對象是一套**已經存在**的系統。所以你要的不是一份題目描述，是一套打得開、點得動、看得到原始碼的東西——需求、流程、資料表與問題，全都要你自己從裡面推導出來。

期中總共有四樣東西會用到，分工不重疊：

| 文件 | 回答的問題 | 什麼時候看 |
|---|---|---|
| 本資料夾的系統 | 這套系統實際怎麼運作、資料長什麼樣 | **從頭到尾** |
| [報告內容](../00-Course-Introduction/Report-Contents.md)〈一〉 | 必做的九項是什麼（規定的事實來源） | 確認要交什麼 |
| [系統分析範例報告說明](../02-Midterm-Project-Example-Reports/Analysis-Phase-Deliverables.md) | 每一項該有哪些欄位、圖怎麼畫 | 動筆寫某一項卻不知道該放什麼時 |
| [系統分析範例報告](../02-Midterm-Project-Example-Reports/Analysis-Phase-Sample-Report.md) | 交出去的成品長什麼樣 | 想知道整份的長相與詳細程度時 |

後面兩份的示範對象是討論區系統（`SAD-Forum/`），詳見〈三〉。

## 二、這些系統不會給你什麼

**不給使用案例圖、不給活動圖、不給你那份報告要的 ERD。**

每套系統的 `document/` 底下確實有規格書與建置流程書，但那是**開發者視角的成品文件**：它從「系統已經是這樣」出發，往下寫功能與資料表。你的報告要走的是相反方向——從畫面與流程往回推「當初為什麼要有這個功能、這張表為什麼長這樣」。兩者的內容看起來會有重疊，推導過程完全不同，而分數在推導過程。

規格書第 11 章列有「已知技術債」。**那是開發者自己知道的部分，不等於這套系統所有的問題。** 第 9 項要的是你從前面八項分析推導出來的問題，照抄那張清單沒有分析依據，訪談一問就出來。

## 三、四套系統一覽

| 系統 | 情境 | 規模 | 這一套要想清楚的問題 |
|---|---|---|---|
| [器材借用系統](SAD-Equipment/README.md)（`SAD-Equipment/`） | 器材登錄、借用申請、審核、登記借出、登記歸還 | 5 個子系統、4 張表 | 可借數量什麼時候才真的扣掉，核准算不算 |
| [活動報名系統](SAD-Events/README.md)（`SAD-Events/`） | 活動建立與報名，含名額、報名期限與活動狀態 | 5 個子系統、4 張表 | 「發起者」不是角色而是關係，權限要看資料而不只看身分 |
| [校園訂餐系統](SAD-Meal-Order/README.md)（`SAD-Meal-Order/`） | 菜單維護、線上訂餐、訂單審核、登記取餐 | 5 個子系統、4 張表 | 份數在哪一步被佔用，訂單取消之後又在哪一步回補 |
| [討論區系統](SAD-Forum/README.md)（`SAD-Forum/`） | 會員帳號的完整生命週期，加上一個討論區 | 5 個子系統、3 張表 | 帳號被停用之後，他已經發出去的內容怎麼算 |

**討論區系統是上課示範用的，不是各組可選的分析題目。** 它是〈一〉那兩份範例報告的分析對象，所以你手上會同時有「系統」與「照著它寫完的報告」。想知道一份分析報告要從系統推導到什麼程度，把它們對照著看最快。

前三套的規模與難度刻意做成相當：都是三個角色、一張主檔加明細的單據、一組會自己算出來的狀態。要想的問題則刻意錯開，不會有兩組交出結構相同的報告。

四套的會員帳號與管理子系統（登入、個人資料、會員管理）是同一套程式，**那是身分基礎不是核心業務**。報告的重心放在借用、報名或訂餐那條流程上，帳號的部分交代清楚角色與權限就好。

## 四、怎麼用這幾套系統

| 步驟 | 做什麼 |
|:--:|---|
| 1 | 先照系統自己的 `README.md` 把它跑起來，用三個種子帳號**各登入一次**。一般使用者、管理員、停用帳號看到的畫面不一樣，這就是角色分析的第一手材料 |
| 2 | 完整走一遍主要流程，從開單走到結案。每一步把畫面截下來，記下「誰按的、按完什麼變了」 |
| 3 | 挑一個功能，從畫面追到資料表：`templates/` 的哪個表單 → `blueprints/` 的哪條路由 → `db/` 的哪個函式 → 哪張表的哪幾欄 |
| 4 | 讀 `document/` 的規格書，對照你走出來的結果。**先自己走一遍再讀**，順序反過來就變成抄文件 |
| 5 | 回頭讀[系統分析範例報告說明](../02-Midterm-Project-Example-Reports/Analysis-Phase-Deliverables.md)開始寫 |

第 1 步不要跳過。多數人一拿到就去看程式碼，結果連系統在做什麼都還沒搞清楚。**先當使用者，再當分析師。**

## 五、四套系統共通的概念

各套自己的功能說明寫在該套的 `README.md` 與 `document/`，這裡只放四套都會出現的。

| 名詞 | 意思 |
|---|---|
| 種子資料 | 系統第一次啟動時自動寫進去的範例資料（帳號、器材、活動、餐點、文章）。它是為了讓你一打開就有東西可看，不是真實資料 |
| 主檔與明細 | 一張單據拆成兩層：主檔記「誰在什麼時候開了哪一種單」，明細記「這張單包含哪幾個項目、各多少」。借用單／借用明細、活動／活動明細都是這個結構 |
| 狀態 | 一張單據目前走到哪一步。**狀態值有幾個、哪些轉移是允許的，是設計出來的，不是天生的**，限制寫在程式裡而不是資料表裡 |
| 算出來的狀態 | 有些狀態不存在資料表中，是每次查詢時用時間或數量現算的（例如活動的「名額已滿」）。**它沒有欄位可以找，只能從程式碼裡看出來** |
| 軟刪除（邏輯刪除） | 按下刪除之後資料還在，只是被標記為已刪除，畫面不再顯示。四套系統都不做真的 `DELETE` |
| 角色與權限 | 系統只存「你是誰」，每次請求重新查你的角色與帳號狀態。**畫面上看不到按鈕，不等於後端禁止那個操作**，這兩件事要分開分析 |
| 共用資源 | 多個人搶同一份東西（器材的可借數量、活動的名額、餐點的剩餘份數）。**檢查的時機與真正使用的時機不見得是同一刻**，兩者之間的落差就是問題所在 |
| 技術債 | 開發時知道有問題、但刻意先不修的地方。規格書第 11 章列的就是這個 |

## 六、拿到系統之後的第一週

**一、把系統操作到會壞。** 欄位留空、數量填超過庫存、日期填成過去、報名同一場兩次、用停用帳號的舊 session 去按送出。**系統擋下你的每一個地方，都是一條需求**；沒擋下的每一個地方，都是第 9 項的材料。

**二、把三個角色的畫面並排。** 同一個頁面，一般使用者、管理員、停用帳號各截一張圖。差異就是權限設計，這是第 2 項與第 5 項最快的入手點。

**三、用自己的話寫下這套系統在解決什麼問題。** 三句話寫不出來就是還沒懂。這一步做完，第 1 項〈問題與系統背景〉就有一半的材料了。

## 七、如果程式碼看不懂

**這是正常的，不是你的問題。** 你們大一只修過基本程式設計，沒學過 Flask、沒學過資料庫，看不懂是預期中的事。而且**期中報告不要求你看懂每一行程式碼**，要求的是看懂系統怎麼運作。

| 順序 | 做什麼 |
|:--:|---|
| 1 | 回到畫面。看不懂的功能，先把它操作十次，觀察輸入什麼、輸出什麼 |
| 2 | 讀 `document/` 對應子系統的那一份文件。它用中文寫，不需要程式基礎 |
| 3 | 只讀函式名稱與註解，不讀函式內容。`create_borrow_order` 這種名字已經告訴你它在做什麼 |
| 4 | 上課問，或問修過程式相關課程的同學 |
| 5 | 問 AI 幫你讀某一段程式碼。但**你必須看懂它給你的東西**，採用之前要能自己說明——懂或不懂，會在口頭報告與個人訪談的問答裡直接顯現出來。使用揭露義務見 [SAD 課程介紹](../00-Course-Introduction/Course-Introduction.md)〈AI 工具使用揭露〉 |

## 八、有幾件事這幾套系統都不要做

| 不要做 | 為什麼 |
|---|---|
| 修改系統的程式碼 | 期中做的是分析不是實作。你改過的系統跟老師手上的不一樣，對不起來 |
| 把規格書第 11 章整段搬進第 9 項 | 那是開發者的清單不是你的分析，而且沒有分析依據 |
| 逐行解釋程式碼 | 報告不是程式導讀。要交的是需求、流程、資料與問題，不是 `app.py` 在做什麼 |
| 把登入、註冊、驗證碼當成核心功能分析 | 四套系統共用同一套帳號子系統，那不是你這一題的重點 |
| 挑剔程式風格、命名與縮排 | 那是程式碼品質，不是系統分析。第 9 項要的是流程、資料或權限層次的問題 |
