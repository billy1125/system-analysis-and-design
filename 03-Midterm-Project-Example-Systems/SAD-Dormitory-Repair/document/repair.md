## 一張報修單的一生

```
住宿生                          宿舍管理員                    維修人員
  │                                 │                            │
  │ ① 申報                          │                            │
  │   標題／類別／優先／地點／描述    │                            │
  ├────────────────► pending ───────┤                            │
  │                                 │ ② 派工（選承辦人）          │
  │  ③ 修改／取消（僅此階段）        ├──────► assigned ──────────►│
  │                                 │                            │ ④ 開始處理
  │  ⑤ 取消（最後機會）              │                     in_progress
  │                                 │                            │ ⑥ 登記完成
  │  ⑦ 回報沒修好（用回覆）          │                     completed
  │                                 │ ⑧ 重新開啟 ──► pending     │
  │                                 │                            │
  │              （或 ② 直接退件 ──► rejected）                   │
```

任何階段雙方都可以在報修單上**回覆**（結案後除外）。每一次狀態異動都會在處理歷程中留下一筆紀錄。

## 畫面一：我的報修單（`GET /repair/`）

只列出**自己申報的**報修單。管理員在此頁看到的也一樣——要看全部請到報修管理。

| 區塊 | 內容 |
|------|------|
| 狀態篩選列 | 全部、待受理、已派工、處理中、已完成、已退件、已取消 |
| 「＋ 我要報修」按鈕 | 右上角 |
| 表格 | 單號、標題（連結）、類別、地點、優先、狀態、承辦人、申報時間、最後異動 |
| 分頁 | 每頁 10 筆 |

排序依**最後異動時間降冪**——有新回覆或狀態異動的單會浮到最上面。

空清單時的文案依情境不同：篩選全部時是「尚未申報任何報修單。宿舍設施有問題請點右上角『我要報修』」；篩選特定狀態時是「沒有『已完成』的報修單」。

## 畫面二：報修表單（`/repair/new`、`/repair/<id>/edit`）

新增與修改共用同一個樣板，欄位完全相同。

| 欄位 | 必填 | 說明 |
|------|:---:|------|
| 報修標題 | ✅ | 一句話描述問題 |
| 維修類別 | ✅ | 給排水／電力照明／家具修繕／網路／空調／門窗鎖具／其他 |
| 優先等級 | ✅ | 低／一般／高／緊急 |
| 宿舍棟別 | ✅ | 以個人資料預填 |
| 房號／地點 | ✅ | 以個人資料預填。**可以是「3 樓走廊」這種非房號** |
| 聯絡電話 | ❌ | 以個人資料預填。留空時詳細頁退回顯示個人資料的電話 |
| 故障情形 | ✅ | 多行文字 |

**地點與電話為什麼是報修單自己的欄位，而不是每次都從個人資料抓：** 報修地點不必然是申報人的房間（走廊的燈、交誼廳的冷氣、洗衣間的水管都會被申報），而且報修單記錄的是**申報當下**的地點——住戶換房之後，舊的報修單仍應指向舊房號。

修改模式多一則提示：「報修單一經派工便無法修改。若要補充資訊，請回到報修單頁面新增回覆。」

### 驗證順序與訊息

1. 標題 → `請輸入報修標題`
2. 故障情形 → `請描述故障情形`
3. 棟別 → `請輸入宿舍棟別`
4. 房號 → `請輸入房號`
5. 類別合法 → `維修類別不正確`
6. 優先等級合法 → `優先等級不正確`

第一個不通過的就回傳，不累積多則。失敗時重新渲染表單並**回填使用者剛填的內容**（不用 flash + redirect，那會沖掉）。

## 畫面三：報修單詳細（`GET /repair/<id>`）

左右兩欄。版面示意見 [`system-spec.md`](system-spec.md) §9.3。

### 左欄上：基本資料

單號、標題、狀態 badge、維修類別、優先等級、報修地點、申報人、聯絡電話、承辦人、申報時間、派工時間、開始處理、結案時間。

未發生的時間欄位顯示 `—`；未派工時承辦人顯示「尚未派工」。

### 左欄下：處理歷程

時間軸由舊到新，三種紀錄以不同顏色的圓點與標籤區分：

| 類型 | 顏色 | 誰產生 | 內容 |
|------|------|--------|------|
| 申報內容 | 藍 | 申報人 | 申報時填的故障情形。一張單恰有一則 |
| 回覆 | 灰 | 申報人或管理員 | 補充說明、約定時間、回報狀況 |
| 狀態異動 | 紫 | 系統（記在執行者名下） | 「已派工給 王師傅：請帶備用燈管」等 |

管理員的紀錄旁會多一個「管理員」標記。

這個視覺區分是刻意的——讀者要能一眼分辨「這句話是人寫的」還是「這是系統記錄的事實」。

### 左欄底：回覆表單

未結案時顯示；已結案時替換成一句說明：

> 此報修單已結案（已完成），不再接受回覆。若問題再次發生，可在右側「重新開啟」。

（若是已退件或已取消，則顯示「若問題仍在，請另外申報一張新的報修單」。）

### 右欄：依身分與狀態渲染的操作

**申報人本人：**

| 狀態 | 可做 |
|------|------|
| 待受理 | 修改報修單、取消報修 |
| 已派工 | 取消報修 |
| 其他 | 無（顯示說明：有問題請在左側新增回覆） |

**管理員：**

| 狀態 | 表單 |
|------|------|
| 待受理 | 派工（承辦人下拉 + 備註）、退件（**原因必填**） |
| 已派工 | 開始處理（備註選填） |
| 處理中 | 登記完成（完工說明選填） |
| 已完成 | 重新開啟（**原因必填**） |
| 已退件／已取消 | 無 |

任何狀態都有「刪除報修單」。

另有一個**狀態流程指示器**（① 待受理 → ② 已派工 → ③ 處理中 → ④ 已完成），標示已完成、目前、未達三種狀態，下方一句話說明退件與取消是離開流程的兩條分支。

## 畫面四：報修管理（`GET /repair/manage`，管理員）

| 區塊 | 內容 |
|------|------|
| 狀態摘要 | 六個可點擊的計數方塊，點擊即篩選 |
| 篩選列 | 全部 + 六個狀態 |
| 搜尋 | 標題、棟別、房號、申報人 email 與姓名 |
| 表格 | 比「我的報修單」多了**申報人**與**操作**兩欄 |

摘要方塊與篩選連結功能重複，保留兩者是因為它們回答不同的問題：摘要回答「現在整體狀況如何」，篩選回答「我要看哪一批」。管理員進入頁面的第一眼需要前者。

## 誰可以做什麼

| 動作 | 申報人 | 其他住宿生 | 管理員 |
|------|:---:|:---:|:---:|
| 檢視 | ✅ | ❌ | ✅ |
| 修改（限待受理） | ✅ | ❌ | **❌** |
| 取消（限待受理／已派工） | ✅ | ❌ | **❌** |
| 回覆（未結案） | ✅ | ❌ | ✅ |
| 派工／開始／完成／退件／重新開啟 | ❌ | ❌ | ✅ |
| 刪除 | ❌ | ❌ | ✅ |

兩個值得說明的「❌」：

**管理員不能修改報修單內容。** 申報內容是住戶對故障的原始證言。管理員若能改，歷程就失真了——事後無從分辨「當初申報的就是這樣」與「有人後來改成這樣」。要補充資訊，用回覆，它會留下作者與時間。

**管理員不能代為取消。** 取消是申報人的權利（「我自己修好了」）。管理員認為不該受理時，該用的是**退件**，而退件強制填寫原因。兩者的差別不只是誰按按鈕，而是誰對這個決定負責。

## 錯誤情境總表

| 情境 | 訊息 | 導向 |
|------|------|------|
| 未登入 | —（直接 redirect） | `/login` |
| 帳號已停用／刪除 | —（清 session） | `/login` |
| 報修單不存在或已刪除 | `報修單不存在或已刪除` | 我的報修單 |
| 檢視他人的報修單 | `無權限檢視此報修單` | 我的報修單 |
| 修改他人的（含管理員） | `無權限修改此報修單` | 該單詳細頁 |
| 修改非待受理的單 | `只有待受理的報修單可以修改` | 該單詳細頁 |
| 取消他人的（含管理員） | `無權限取消此報修單` | 該單詳細頁 |
| 取消處理中之後的單 | `無法取消此報修單（狀態不符）` | 該單詳細頁 |
| 回覆已結案的單 | `此報修單已結案，無法新增回覆` | 該單詳細頁 |
| 回覆內容為空 | `請輸入回覆內容` | 該單詳細頁 |
| 住宿生執行管理動作 | `無操作權限` | 我的報修單 |
| 派工未選承辦人 | `請選擇承辦人` | 該單詳細頁 |
| 派給住宿生或停用的管理員 | `派工失敗（報修單狀態不符，或承辦人不是啟用中的管理員）` | 該單詳細頁 |
| 退件未填原因 | `請填寫退件原因` | 該單詳細頁 |
| 重新開啟未填原因 | `請填寫重新開啟的原因` | 該單詳細頁 |
| 狀態不符的轉移 | `無法…（報修單狀態不符）` | 該單詳細頁 |

## 種子報修單

系統初次啟動會植入六張報修單，涵蓋六個狀態各一張。它們的用途是讓每個狀態的畫面**開箱即可觀察**，不必自己一步步操作出來。

| # | 標題 | 狀態 | 值得看什麼 |
|---|------|------|-----------|
| 1 | 浴室水龍頭持續漏水 | 待受理 | 只有申報內容的最小案例 |
| 2 | 房間日光燈管閃爍 | 已派工 | 狀態紀錄帶備註的樣子 |
| 3 | 冷氣不冷且有異音 | 處理中 | 三種紀錄類型並存的時間軸 |
| 4 | 衣櫃門把鬆脫 | 已完成 | 走完全程，含雙方來回討論 |
| 5 | 想在房間加裝個人洗衣機 | 已退件 | 申報人是停用帳號，姓名欄退回顯示 email；退件原因寫得很完整 |
| 6 | 走廊燈泡不亮 | 已取消 | 地點是「3 樓走廊」而非房號 |

第 5 張同時示範了兩件事：帳號被停用不影響他已申報的紀錄；申報人沒填姓名時系統如何退回顯示。

## 已知限制

| 項目 | 說明 |
|------|------|
| 時間顯示為 UTC | 在台灣使用時每個時間都慢 8 小時（KI-25） |
| 無圖片附件 | 報修最常被要求的功能（KI-27） |
| 無通知 | 狀態改變不會通知申報人，雙方都要自己回來看（KI-28） |
| 清單無排序切換 | 固定依最後異動時間，找不出「最緊急」或「等最久」的單（KI-29） |
| 無滿意度回饋 | 無法區分「真的修好了」與「住戶懶得再回報」（KI-30） |
| 承辦人可能已離職 | 停用或降級不會從報修單移除（KI-14） |
| 個資存取無稽核 | 有權限控制（誰能看），但沒有紀錄（誰看過）（KI-11） |
