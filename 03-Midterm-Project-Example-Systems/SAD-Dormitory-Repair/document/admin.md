# 會員管理系統（admin）

> 開發規範見 [`blueprints/admin/CLAUDE.md`](../blueprints/admin/CLAUDE.md)；完整規格見 [`system-spec.md`](system-spec.md) §5.5。

本子系統幾乎不受應用領域影響——一個治理帳號的子系統，換成任何一個領域都長得差不多。

---

## 功能

| 路由 | 功能 |
|------|------|
| `GET /admin/users` | 會員清單 |
| `GET /admin/users/<id>` | 會員明細 |
| `POST /admin/users/<id>/activate` | 啟用 |
| `POST /admin/users/<id>/deactivate` | 停用 |
| `POST /admin/users/<id>/role` | 調整角色 |
| `POST /admin/users/<id>/delete` | 軟刪除 |

全部需要：已登入 → 帳號可用 → 管理員（`role = 0`）。

---

## 畫面一：會員清單

| 區塊 | 內容 |
|------|------|
| 篩選連結 | 全部／啟用中／已停用／已刪除 |
| 搜尋 | email、姓名、顯示名稱、**房號** |
| 表格 | ID、Email、姓名、**住宿位置**、**聯絡電話**、角色、狀態、建立時間、最後登入、操作 |
| 分頁 | 每頁 10 筆 |

篩選、搜尋、頁碼三者可組合（`?status=active&q=301&page=2`）。

**住宿位置與聯絡電話兩欄是本系統新增的**，搜尋也新增比對房號。管理員找人時，「A 棟 301 是誰住的」跟「陳小明的 email 是什麼」一樣常見。

目前登入的帳號那一列會以淺藍色標示，操作欄顯示「（目前登入帳號）」而非按鈕。

### 狀態與角色標記

| 標記 | 條件 |
|------|------|
| 已刪除（灰） | `is_deleted = 1`（優先判斷） |
| 啟用中（綠） | `is_active = 1` |
| 已停用（橘） | `is_active = 0` |
| 管理員（藍） | `role = 0` |
| 住宿生（灰） | `role = 1` |

## 畫面二：會員明細

三個區塊：

**資料卡**——ID、Email、姓名、顯示名稱、**宿舍棟別**、**房號**、**聯絡電話**、角色、啟用狀態、刪除狀態、建立時間、最後登入。

**報修單區塊（本系統新增）**——列出該會員最近 5 筆報修單（單號、標題連結、最後異動），並附一句說明：

> 停用或刪除帳號**不會**連動刪除這些報修單——設施的維護歷程屬於宿舍，不屬於個人。

沒有紀錄時顯示「此會員尚未申報過任何報修單」。

**加這個區塊的理由**：管理員在停用或刪除帳號之前，應該先看到會受影響的紀錄。而本系統的行為是不連動刪除，這個決定必須在管理員動手的那個畫面上說清楚，不能只寫在文件裡。

> 這個區塊刻意**不顯示報修狀態**。狀態的中文標籤定義在 `repair` Blueprint 內，`admin` 若要顯示就得跨 Blueprint 取用或自行複製一份標籤表——兩者都會弄髒模組邊界。而這個區塊真正要回答的問題是「有沒有紀錄」，單號與標題就夠了。
>
> 這是一個很小的取捨，但它示範了模組邊界如何實際影響功能設計：**當一個功能需要跨越邊界時，先問這個功能是不是真的需要那個資訊。**

**操作卡**——依被檢視者的狀態顯示不同內容：

| 被檢視者 | 顯示 |
|---------|------|
| 就是自己 | 「這是您目前登入的帳號，不可對自己執行停用、刪除或角色調整。」 |
| 已刪除 | 「此帳號已刪除，無法再執行任何操作。」 |
| 其他 | 角色下拉 + 更新按鈕；停用／啟用按鈕；刪除按鈕（含 `confirm`） |

被檢視者在樣板中命名為 `target`，**刻意不叫 `user`**，避免與 topbar 顯示的當前登入者混淆。

## 三層權限檢查（順序不可調換）

```
1. 已登入？        否 → redirect /login
2. 帳號可用？      否 → session.clear() + redirect /login
3. role == 0？    否 → flash「無操作權限」+ redirect /
```

第 2 層失敗代表**身分本身失效**，處置是登出；第 3 層失敗代表**身分有效但權限不足**，處置是導回首頁。

若把第 3 層放前面，一個 `role = 0` 但已被停用的帳號會收到「無操作權限」——這與事實不符（他的權限沒問題，是帳號沒了），而且 session 不會被清除。

`tests/test_admin.py` 的 `test_user_list_disabled_admin_redirects_to_login` 專門驗證這個順序。

## 自我保護規則

| 規則 | 內容 | 訊息 |
|------|------|------|
| R1 | 不可停用自己 | `不可停用自己的帳號` |
| R2 | 不可刪除自己 | `不可刪除自己的帳號` |
| R3 | 不可修改自己的角色 | `不可修改自己的角色` |

**啟用不設自我限制**——對自己啟用是無害且冪等的。

**限制只針對自己，不針對所有管理員。** 管理員之間可以互相停用、刪除、調整角色。種子帳號 `staff@example.com` 存在的理由之一就是讓這件事測得出來。

### 為什麼不做「最後一個管理員」檢查

由 R1–R3 可推得：任何管理動作完成後，執行者仍是一個啟用、未刪除、`role = 0` 的帳號。因此系統中永遠至少有一個可用的管理員，「最後一個管理員被鎖死」的狀態**不可達**。

系統因此不實作管理員計數檢查——不是忘了做，是推導出不需要。

> ⚠️ 若未來放寬 R1–R3 任何一條，必須立即補上「操作後啟用中管理員數 ≥ 1」的檢查，否則系統可被鎖死且無法從介面復原。

## 每個動作的檢查順序

三層守門之後，四個 POST 動作各自再檢查：

1. 目標存在？ → `找不到該使用者`
2. 目標非自己？（activate 除外）→ R1／R2／R3 的訊息
3. 目標未被軟刪除？ → `該帳號已刪除，無法操作`
4. （僅 role）值為 `'0'` 或 `'1'`？ → `角色值不正確`

順序固定。第 2 步在第 3 步之前，因此對自己執行時得到的是「不可停用自己」而不是別的訊息。

全部成功後 flash 對應訊息並 redirect 回清單（**不是明細頁**）——管理員通常要連續處理多筆。

## 停用與刪除的實際後果

| 對象 | 停用（`is_active = 0`） | 軟刪除（`is_deleted = 1`） |
|------|------------------------|---------------------------|
| 登入 | 「帳號已停用」 | 「帳號或密碼錯誤」 |
| 持有舊 session | 下一個請求就被清除 | 同左 |
| 個人資料的修改 | **被擋下**（本系統的修正，見 `profile.md`） | 同左 |
| 已申報的報修單 | **完全不受影響** | **完全不受影響** |
| 作為承辦人 | 仍掛在報修單上（KI-14） | 同左 |
| 在清單中 | `?status=disabled` 可見 | `?status=deleted` 可見 |
| 還原 | 可以（啟用） | **不可以**（介面上沒有還原功能，紀錄仍在資料庫中） |

**報修單完全不受影響是刻意的設計。** 報修紀錄是宿舍設施的維護歷程，屬於宿舍，不屬於個人。學生畢業退宿之後，「A 棟 301 的冷氣去年修過三次」這件事仍然要查得到——下一個住進去的人、編列維修預算的人、判斷該不該整台換掉的人，都需要這段歷史。

若某天的需求變成「退宿後個資必須清除」，正確的做法不是刪除報修單，而是**匿名化**：把 `requester_id` 指向一個保留帳號、清空 `contact_phone`，保留其餘欄位。這個取捨值得與 GDPR 的「被遺忘權」一起討論。

## 已知限制

| 項目 | 說明 |
|------|------|
| 軟刪除無法還原 | 沒有 restore 功能，紀錄還在但介面上救不回來 |
| 頁碼超出範圍不報錯 | `?page=999` 回傳空清單與「第 999 / 2 頁」（KI-16） |
| 搜尋未 escape `%` 與 `_` | 僅影響搜尋語意，不是 SQL injection（KI-17） |
| 無操作稽核 | 誰在何時停用了誰，系統沒有紀錄 |
| 無批次操作 | 一次只能處理一個帳號 |
| 停用不處理其名下的報修單 | 承辦人可能已離職（KI-14） |
