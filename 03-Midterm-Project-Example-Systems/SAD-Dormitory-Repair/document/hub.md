理由寫在頁面上，而不只是寫在文件裡。讀原始碼的人與用系統的人會問同一個問題（「為什麼不給看」），答案應該在他們各自看得到的地方。

### 內嵌登入

右側的登入表單與 `/login` 功能完全相同：同樣的五道驗證、同樣的五則訊息、同樣的驗證碼機制。

> **已知問題（KI-12）**：這段程式碼是 `auth.login_page()` 的完整複製。任何登入政策的強化都**必須兩處都改**。

## 帳號失效時的行為

若 session 中的 `user_id` 對應的帳號已被停用或軟刪除：

1. `session.clear()`
2. **以訪客視圖渲染，回傳 200**

**不 redirect 到 `/login`。** 若改成 redirect，被停用的使用者會陷入「點首頁被踢到登入頁」的體驗，但他其實只是想看看首頁。首頁應該容許訪客。

其他子系統的做法不同：`profile`、`admin`、`repair` 在帳號失效時都是 `session.clear()` + redirect `/login`，因為它們沒有訪客版本可以退回。

## 摘要數字的來源

```python
_, my_request_total = db.list_my_requests(user['id'], 1, 1, 'all')
pending_count       = db.count_by_status()['pending']   # 僅管理員
```

第一行用 `page_size=1` 只是為了取回傳 tuple 的第二個元素（總數）。這會浪費一次索引查詢（撈出一筆用不到的資料），但省下再寫一個 `count_my_requests()` 函式。在本系統的規模下是划算的取捨；若首頁成為效能瓶頸，這是第一個該改的地方。

第二行只在管理員時執行——住宿生看不到那張卡片，查了也沒用。

## 已知限制

| 項目 | 說明 |
|------|------|
| 內嵌登入是複製 | 與 `auth.login_page()` 逐行相同（KI-12） |
| 摘要查詢有浪費 | 為取總數而撈出一筆用不到的資料 |
| 卡片數量寫死在樣板 | 新增子系統要手動加卡片，沒有註冊機制 |
