# 登入系統（auth）

> 開發規範見 [`blueprints/auth/CLAUDE.md`](../blueprints/auth/CLAUDE.md)；完整規格見 [`system-spec.md`](system-spec.md) §5.2。

---

## 功能

| 路由 | 功能 |
|------|------|
| `GET POST /login` | 登入 |
| `GET POST /register` | 申請帳號 |
| `GET /captcha.png` | 驗證碼圖片 |
| `GET /logout` | 登出 |

---

## 登入

### 畫面

標題「系統分析與設計／校園宿舍報修系統 v1.0／登入」，三個欄位：電子郵件、密碼、驗證碼（圖片可點擊刷新，旁邊有 `↻` 按鈕）。底下是「登入」與「申請帳號」兩個按鈕。

### 資料流

```
POST /login
  → 驗證碼非空？             否 → 「請輸入驗證碼」
  → 驗證碼相符？（不分大小寫） 否 → 「驗證碼錯誤，請重新輸入」
  → 帳密皆非空？             否 → 「請輸入帳號與密碼」
  → db.find_user_by_email()
  → 帳號存在且未刪除且密碼正確？ 否 → 「帳號或密碼錯誤」
  → 帳號啟用中？             否 → 「帳號已停用」
  → db.update_last_login()
  → session['user_id'] = user['id']
  → redirect /
```

已登入者存取 `/login` 直接 redirect `/`。

### 兩個訊息設計

**「帳號不存在」「密碼錯誤」「帳號已刪除」共用同一則訊息。** 不讓外部探測某個 email 是否註冊過。

**但「帳號已停用」是不同的訊息。** 這是刻意的取捨：停用是管理員的行政處置（例如退宿），當事人有權知道自己為何登不進去，否則他會一直懷疑是自己記錯密碼。

## 申請帳號

### 畫面欄位

| 欄位 | 必填 | 提示 |
|------|:---:|------|
| 電子郵件 | ✅ | example@mail.com |
| 密碼 | ✅ | 至少 8 個字元 |
| 確認密碼 | ✅ | 再次輸入密碼 |
| 姓名 | ❌ | 選填 |
| 宿舍棟別 | ❌ | 選填，例如 A 棟 |
| 房號 | ❌ | 選填，例如 301 |
| 聯絡電話 | ❌ | 選填，維修人員聯繫用 |

### 資料流

```
POST /register
  → email 與密碼皆非空？  否 → 「請輸入電子郵件與密碼」
  → email 格式正確？      否 → 「電子郵件格式不正確」
  → 密碼長度 ≥ 8？        否 → 「密碼至少需要 8 個字元」
  → 兩次密碼一致？        否 → 「兩次密碼輸入不一致」
  → db.create_user()
      └ IntegrityError   → 「此電子郵件已被使用」
  → flash「申請成功，請登入」
  → redirect /login
```

驗證失敗時**重新渲染表單並回填**已填的內容（email、姓名、三個住宿欄位），不用 flash + redirect。

新帳號一律 `role = 1`（住宿生）、`is_active = 1`。系統沒有「申請成為管理員」的途徑，只能由既有管理員在會員管理中指定。

### 為什麼住宿資料是選填

直覺上報修系統的使用者一定住宿舍，房號應該必填。但有兩個反例：

- 新生在分配房間之前就會拿到帳號
- 管理員與維修人員根本不住宿舍（種子帳號 2 與 4 的棟別就是空的）

設成必填等於要求所有管理員帳號都編一個假房號。因此改為選填，而在真正需要的地方（報修表單）才必填——**在需要的那一刻才要求**。

申請表單也不收「顯示名稱」，使用者可以之後在個人資料頁補。理由是表單已經有七個欄位了。

## 驗證碼

`GET /captcha.png` 產生一張 160×50 的 PNG，答案寫入 `session['captcha']`。

字元集為 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`，共 5 碼——**刻意排除易混淆的 `I` `O` `0` `1`**。比對時不分大小寫。

點擊圖片或按 `↻` 都會重新請求這個 URL（附加 `?t=` 時間戳繞過瀏覽器快取），伺服器產生新答案並覆寫 session。

> **已知問題（KI-05）**：登入成功後 `session['captcha']` 未清除，因此同一組答案可以重複使用。攻擊者人工辨識一次就能無限次嘗試密碼，驗證碼作為防自動化機制形同虛設。這是全系統修補成本最低、安全效益最高的一項。

## 登出

`GET /logout` → `session.clear()` → redirect `/login`。

> **已知問題（KI-07）**：這是 GET 卻有副作用，違反本專案自己的規範（`rules/flask-blueprint.md` 規定有副作用的動作一律用 POST）。可被 `<img src="/logout">` 之類的方式從外站觸發。危害輕微，但它是規範與實作不一致的明確案例。

---

## 注意事項

**首頁的內嵌登入表單是這裡的完整複製（KI-12）。** `blueprints/hub/__init__.py` 中有一段與 `login_page()` 逐行相同的程式碼。任何登入政策的強化都**必須兩處都改**，漏改就能從另一個入口繞過。

## 已知限制

| 項目 | 說明 |
|------|------|
| 驗證碼可重放 | 登入成功後未清除（KI-05） |
| 無失敗次數限制 | 可暴力破解；資料模型層面就不支援鎖定（KI-02） |
| 無 CSRF token | 所有 POST 表單皆無（KI-01） |
| 無 session fixation 防護 | 登入時未先 `session.clear()`（KI-08） |
| 密碼規則只有長度 | 無複雜度要求；bcrypt 靜默截斷 72 bytes；**無變更密碼與忘記密碼功能**（KI-06） |
| 種子帳號密碼公開 | 且 bcrypt cost 刻意調低（KI-10） |

KI-02 + KI-05 + KI-10 三者疊加後，管理員帳號可被自動化爆破。**三者單獨看都不算致命，合起來就是。**
