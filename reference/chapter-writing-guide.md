# 教材撰寫規範

本檔為「系統分析與設計」課程教材各章正文（`0X-XXX.md`）的完整撰寫規範。撰寫新章節前請先讀完本檔，再複製 `reference/chapter-template.md` 作為起點。投影片版本另有規範，見 `reference/slides-design-template.md`。

`CLAUDE.md` 只保留最容易出錯的幾條摘要，細節一律以本檔為準；兩邊若有衝突，以本檔為準並回頭修正 `CLAUDE.md`。

## 一、語言與讀者程度

所有內容必須以繁體中文、台灣習慣的工程與資訊用語撰寫，避免中國大陸慣用譯名（例如寫「軟體」而非「軟件」、寫「程式」而非「程序」）。技術名詞首次出現時附上英文全名，格式為「中央處理器（CPU）」，後續再出現即可直接使用中文或縮寫。

讀者是沒有程式設計背景的工業工程與管理系大學部學生。說明技術概念時不要假設讀者知道任何未經解釋的專業術語；若必須使用，就在該處用一兩句話解釋，或改以工業場域的類比帶入。判斷標準是：一個修過工業工程基礎課、但沒寫過程式的學生，能不能只靠這一段文字讀懂。

中文語句的標點一律使用全形（，。、；：？！「」『』（）——……），數字、英文單字與程式碼識別字使用半形，中英文之間、中文與數字之間加一個半形空白。半形括號只用於純英文或數字內容（如 `(v2.1)`），夾雜中文時改用全形括號。程式碼區塊、檔名、路徑、URL 與英文註解不套用此規則。

## 二、Markdown 格式

教材內文以在 GitHub 上直接閱讀為主要情境，因此一律使用標準 CommonMark 語法，避免內嵌 HTML 或各家剖析器不通用的延伸語法（如 `:::` 提示框、上標下標標記）。需要簡報或 PDF 版本時，另外以 Marp 撰寫對應的 `0X-XXX.slides.md`，不要為了投影片效果而在正文中加入 Marp 專用指令。

## 三、粗體標記前後留空白

粗體文字的前後 `**` 標記，只要 **直接貼著中文字或英數字**，就在標記外側補一個半形空白——開頭 `**` 的前面補、結尾 `**` 的後面補。原因是 `**` 緊貼中文字時，部分 Markdown 剖析器偶爾會辨識失敗，導致粗體不生效而把星號原樣印出來。

但外側若已經是全形標點（`，。、；：」）` 等）、半形標點、空白，或位於行首行尾，則 **不補** 空白，否則會在全形標點前多出一個空格（違反中英夾雜的空白規範），或在行首產生多餘縮排。

```markdown
✅ 這是 **重點** 內容
✅ **GPU（圖形處理器）** 原為遊戲設計
✅ 這一節的重點是 **需求訪談**，下一節談原型製作。
❌ 這是**重點**內容
❌ 這一節的重點是 **需求訪談** ，下一節談原型製作。
```

此規則同樣適用於 `.slides.md`。

## 四、圖片

圖片依所屬文章分類，放於 `images/文章檔名/` 資料夾（例如 `images/01-XXX/`），以相對路徑引用，路徑分隔一律使用正斜線 `/`：

```markdown
![說明文字](images/01-XXX/data-flow-diagram.png)
```

檔名一律使用小寫連字號（kebab-case）風格，不使用中文檔名、空白或底線。

### 4.1 圖說標註

每張圖片下方需空一行後，附上一行斜體圖說標註來源。三種來源對應三種格式，不可混用：

| 圖片來源 | 圖說格式 |
|---|---|
| AI 生成 | `*本圖由 ChatGPT 生成，已由作者審核內容正確性*` |
| 作者自製（親手繪製的示意圖、親自拍攝的照片、螢幕截圖） | `*本圖由作者自製*` |
| 外部來源（維基共享資源等） | `*圖片來源：[來源名稱「檔案名」](檔案頁面網址)，作者 XXX，授權 CC BY-SA 3.0*` |

特別注意不要把真人照片或螢幕截圖誤標為 AI 生成。作者自製涵蓋所有非 AI 產出的人工素材，包含手繪與拍攝。

外部來源的圖說必須是含作者與授權條款的完整格式，連結須指向該圖片在 Wikimedia Commons 等平台上的 **檔案頁面**（File page），而非使用該圖的條目頁面（Article page），因為授權資訊只寫在檔案頁面上。

### 4.2 授權查核

下載外部圖片前，務必先在檔案頁面確認授權條款，避免使用僅限「合理使用／fair use」的非自由版權圖片。無法確認授權的圖片一律不可收錄，寧可改用 AI 生成或自行繪製的替代圖。

### 4.3 圖片尺寸

圖片尺寸請選 1000px 以下的縮圖版本。Wikimedia 的檔案頁面可直接取得 `960px-` 等縮圖網址，直接下載縮圖即可。避免收錄動輒數百 KB 的原始大圖，那會拖慢在 GitHub 上的閱讀速度，而教材圖片的顯示寬度本來就不需要那麼大。

## 五、圖片授權例外

外部來源圖片依其原始授權條款使用，不適用本專案未來 `README.md` 所宣告的 CC BY-NC-SA 授權。每收錄一張外部圖片，就需在 `README.md` 的〈📄 授權與使用聲明〉中將它列為例外項目，註明來源與授權條款。

## 六、章節結構

各章正文以 `# 章節標題——工業工程管理導向` 開頭，破折號使用全形。內文小節以 `## {中文數字}、小節標題` 編號（一、二、三……），不使用阿拉伯數字，小節之下如需再分層才使用 `###`。

章節的收尾順序固定為：`## {中文數字}、學習重點總結`（最後一個編號小節）、`## 參考文獻`、`---`、斜體結語。

## 七、參考文獻

各章的 `## 參考文獻` 一律以 **APA 格式** 撰寫，全部為 **英文** 條目，以無序清單呈現、每筆一行，並依 **第一作者姓氏字母** 排序（同作者再依年份先後）。新增文獻時務必插入正確的字母位置，維持整份清單排序一致，不要圖方便附加在清單末尾。

內容應兼顧兩類來源。一類是 **經典教科書**，即系統分析與設計領域公認的課本，如 Dennis、Kendall、Pressman、Sommerville、Yourdon 等人的著作；另一類是 **原典或里程碑論文**，如 Royce 1970 的瀑布模型論文、Chen 1976 的實體關係模型論文、UML 與敏捷方法的原始文獻等。期刊論文、會議論文與技術標準若有 DOI 或穩定網址則附上。書名與期刊名使用斜體。數量以各章約 20 筆以上為原則。

清單之後空一行、以 `---` 分隔，再接一段斜體結語，說明本章用途與延伸練習建議。

## 八、學習重點總結

各章的最後一個編號小節固定為 `## {中文數字}、學習重點總結`，緊接在 `## 參考文獻` 之前，全專案格式一致。

寫法為：先寫一句固定引言「讀完本章後，你應該能夠理解以下核心概念，並將其應用於工業場域的思考與決策：」，接著以 5–6 個 **粗體要點標題** 分段，不使用 `###`，也不使用條列。每個要點標題下方以一段散文說明該概念的內涵，並帶到它在工業場域的意義。

要點是本章核心概念的收束與提煉，不是小節標題的複述。若發現要點標題和小節標題幾乎一字不差，就代表這一節寫成了目錄而非總結，需要重寫。

小節最後以 `> **銜接提示**` 收尾，前指下一章；終點章不需銜接提示。

## 九、延伸閱讀連結

技術名詞、歷史人物與事件首次出現時，附上中文維基百科連結作為延伸閱讀：

```markdown
[資料流程圖](https://zh.wikipedia.org/wiki/資料流程圖)
```

同一個名詞在同一章內只需在首次出現時加連結，之後重複出現不再加，以免影響閱讀。

## 十、跨章連結格式

連結文字使用 **完整檔名**（如 `[05-XXX.md](05-XXX.md)`）而非「05 章」這類序號稱呼，因為章節順序可能調整而檔名相對穩定。指涉某一小節時，用書名號〈〉寫在連結 **外面**（如〈三、需求訪談技巧〉），不使用 `.md#anchor` 形式的錨點連結。

跨章指涉共四種句型，一律使用 blockquote：

| 句型 | 用途 |
|---|---|
| `> **延伸閱讀**` | 本章對某主題點到為止，把讀者推給專門處理該主題的章節 |
| `> **前情提要**` | 回指先前章節已建立的概念 |
| `> **銜接提示**` | 章末前指下一章，寫在〈學習重點總結〉的結尾 |
| 章末斜體註記 | 參考文獻之後的結語段落，說明本章用途與延伸練習建議 |

範例：

```markdown
> **延伸閱讀**：資料建模的完整做法見 [05-XXX.md](05-XXX.md)〈三、實體關係圖〉，本章僅說明它在需求分析階段扮演的角色。
```
