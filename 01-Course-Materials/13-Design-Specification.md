# 系統設計規格與追溯

到這裡，你手上已經有一整疊東西：問題定義、使用案例、需求清單、功能模組、活動圖、循序圖、概念類別圖、實體關聯圖、資料字典、架構圖、介面規格、畫面原型、可行性與風險分析。

**但一疊文件不等於一套設計。** 把它們裝訂在一起交出去，讀者仍然無法回答一個最基本的問題：這些東西講的是同一套系統嗎？

這正是本章要處理的事。系統設計規格書的價值不在於它收錄了什麼，而在於它證明了 **各份文件彼此一致、每一項設計都追溯得回某個需求、任何人接手都看得懂為什麼要這樣做**。這三件事做到了，這疊文件才成為一套可以交付給資訊人員實作的設計。

本章是這本教材的最後一章，也是唯一一章不介紹新的分析方法。它要做的是把前面十二章的產出收束起來，並且交給你一組交件前可以自己跑一遍的檢查。

> **前情提要**：本章假設你已完成前面各章的所有產出。如果還有哪一項沒做，先回頭補完再讀本章——本章談的是怎麼把它們串起來，串的前提是東西都在。

> **延伸閱讀**：這一項在報告中要交什麼，見[「報告內容」](../00-Course-Introduction/Report-Contents.md)期末第 8 項。

> **期末必讀標記**：標題後加註 🔵 期末必讀 的小節，是期末小組報告八項產出直接會用到的內容。判準見[「系統設計範例報告說明」](../04-Final-Project-Example-Reports/Design-Phase-Deliverables.md)，成品的樣子見[「系統設計範例報告」](../04-Final-Project-Example-Reports/Design-Phase-Sample-Report.md)。未標記的小節仍屬課程範圍，只是期末不會直接產出。

## 一、規格書不只是裝訂 🔵 期末必讀

### 1.1 它要通過的測試 🔵 期末必讀

一份合格的設計規格書要通過一個測試：**把它交給一個沒有參與過的人，他能不能照著做出這套系統？**

這個測試比看起來嚴格。它意味著：

- 每一項功能都要有人說得出它為什麼存在（追溯得到需求）。
- 每一個設計決定都要有理由（為什麼選這個架構、為什麼這樣切模組）。
- 各份文件之間不能互相矛盾（同一件事在五個地方講法一致）。
- 還沒解決的問題要標示出來，不能假裝不存在。

**第四項最容易被忽略**，但它其實是專業程度的指標。一份標示了「這三個問題尚待與客戶確認」的規格，比一份看起來每個角落都填滿的規格可信得多。

### 1.2 讀者是誰 🔵 期末必讀

規格書的主要讀者有三種，各自要從裡面找到不同的東西：

| 讀者 | 想找到什麼 |
|---|---|
| 開發人員 | 我要做什麼、資料長什麼樣、畫面有哪些欄位 |
| 使用者代表 | 我要的東西有沒有被涵蓋、我的作業方式會怎麼改 |
| 接手維護的人 | 這件事當初為什麼要這樣做 |

第三種讀者常被遺忘，但一套系統的維護期遠比開發期長。**三年後接手的人看不懂當初的理由，就只能猜，而猜錯的代價是改壞既有功能。** 這也是〈五〉要求留下設計決策紀錄的原因。

## 二、內容架構 🔵 期末必讀

### 2.1 建議的結構 🔵 期末必讀

規格書把前面各章的產出依邏輯順序組織起來，建議的架構：

| 章節 | 內容 | 來自哪一章 |
|---|---|---|
| 1. 設計基礎與需求摘要 | 問題背景、主要角色、核心流程、關鍵需求、系統邊界 | 問題定義、使用者分析、需求分析 |
| 2. 功能與模組設計 | 模組劃分、各模組的目的與輸入輸出、模組關係 | 功能分析 |
| 3. 主要流程與互動設計 | 活動圖、循序圖 | 行為建模 |
| 4. 資料設計 | 概念類別圖、ERD、Schema、資料字典 | 物件建模、資料建模 |
| 5. 系統環境、架構與資料交換 | 架構圖、外部介接規格 | 系統環境與架構、系統介面 |
| 6. 使用者介面設計 | 畫面清單、線框圖或原型、欄位對照 | 使用者介面設計 |
| 7. 可行性、限制與風險 | 四面向可行性、限制盤點、風險登記 | 可行性與風險 |
| 8. 追溯與設計決策 | 追溯表、設計決策紀錄、待解問題 | 本章 |

這個順序正好是期末報告八項的順序，因為那份清單本來就是照這個邏輯排的。**章節名稱可以自己取，內容要找得到。**

### 2.2 第 8 章不是附錄 🔵 期末必讀

前七章是產出，第八章是把產出串起來的東西。**很多組別把它當成收尾的附錄隨便寫**，但它才是「文件間一致性與可追溯性」這個評量面向最直接的證據，也是本章接下來要展開的重點。

## 三、追溯鏈 🔵 期末必讀

### 3.1 最低要求的五段 🔵 期末必讀

追溯是指從一個東西找得到它的來源與去向。本課程要求的最低追溯鏈有五段：

**需求 → 功能模組 → 流程／互動 → 資料 → 畫面**

每一段的意思是：

| 段落 | 回答 |
|---|---|
| 需求 → 模組 | 這條需求由哪個模組負責 |
| 模組 → 流程 | 這個模組的功能在哪一段流程裡被執行 |
| 流程 → 資料 | 這段流程讀寫哪些資料 |
| 資料 → 畫面 | 這些資料在哪個畫面上被輸入或顯示 |

### 3.2 一條完整的追溯範例 🔵 期末必讀

以訪客登記系統為例，挑一條關鍵需求走完全程：

| 段落 | 內容 |
|---|---|
| 需求 | FR-013：當申請的來訪日期不是今天時，系統應要求接待員確認後才可辦理報到，並記錄實際報到日期 |
| 來源 | UC-01 例外流程；訪談發現現場確實會有超量生產 |
| 角色 | 接待員觸發；警衛室領班承受後果（要核對非當日報到的紀錄） |
| 模組 | M2 大門報到與離廠 |
| 流程 | 活動圖「辦理訪客報到」的判斷節點 D2 與動作 A4 |
| 互動 | 系統循序圖中 `alt 累計數超過需求量` 片段 |
| 資料 | 來訪紀錄.visit_date 與系統當日日期比較（**比較的結果是推導值，不是欄位**） |
| 畫面 | 櫃台報到畫面的非當日確認對話框 |
| 設計決策關聯 | D-02（累計數量不存成欄位） |
| 風險關聯 | 無 |

**這樣一條追溯，證明了七份文件在講同一件事。** 期末報告要求「至少選幾項關鍵需求」做完整追溯——三到五條就夠，但每一條都要走完全程。

**其中至少要有一條是非功能需求。** 非功能需求的追溯比功能需求難得多，也最能看出程度：一條「訪客個資自最後一次來訪起保存兩年」的需求，追下去可能同時牽動一個模組、五個欄位、一個畫面與一項定期批次，還連出兩項設計決策、一條風險與一個待解問題。**只追功能需求的報告，這一項拿不到高分**——因為功能需求本來就是照著清單一路做下來的，追不動的地方永遠出現在非功能需求上，而那些地方才是設計的破口。

### 3.3 追溯表怎麼呈現 🔵 期末必讀

實務上會做成一張橫向的表，一列一條需求：

| 需求編號 | 模組 | 流程 | 資料 | 畫面 |
|---|---|---|---|---|
| FR-010 | M2 | 活動圖 A1 | 來訪紀錄.visit_no | 櫃台報到 |
| FR-013 | M2 | 活動圖 D2、A4 | 來訪紀錄.visit_date | 櫃台報到（確認框） |
| FR-014 | M2 | 循序圖訊息 3 | 來訪紀錄（整筆） | 櫃台報到 |
| FR-021 | M4 | 活動圖 B3 | 婉拒紀錄 | 申請確認 |

**空格是有意義的。** 某一列的「畫面」欄空著，代表這條需求沒有任何使用者介面——那可能是正確的（背景自動處理、或那是一條純粹的介面需求所以模組欄才空），也可能是漏了。空格逼你回答這個問題；空得有道理的要寫一句話說明，一條功能需求的模組欄空著就是真的漏了。

**這張表要往兩個方向掃，不是只有一個。**

| 方向 | 問題 | 發現了代表什麼 |
|---|---|---|
| 由左往右 | 有沒有需求對不到任何模組、資料或畫面 | 這條需求沒有被設計出來 |
| 由右往左 | 有沒有模組、資料表或畫面對不到任何需求 | 這個東西是憑空多出來的 |

第二個方向很少人做，卻常常有收穫。**設計時很容易「順手」多加一張表或一個畫面**，當下覺得有用，回頭對矩陣才發現它不對應任何需求——那不是加分，是一份沒有人要求、卻要有人維護的東西。

### 3.4 涉及外部系統時多一段 🔵 期末必讀

如果題目有外部介接，追溯鏈要多接一段：**資料 → 交換關係**。也就是說明這份資料有沒有從外部系統來、或要送到外部系統去。

以員工資料為例：員工.department 這個欄位來自人資系統的 `DEPT_CD` 欄位（需查對照表把代碼轉成名稱），這件事要在追溯表上看得到，否則讀者不知道這個值不是本系統產生的。

### 3.5 做了類別圖或 API 的延伸

有做概念類別圖或 REST API 規格的組別，可以把追溯鏈延伸成：

**需求 → 模組 → 流程／互動 → 類別 → 資料表 → API → 畫面**

**但這不是最低要求。** 依[「報告內容」](../00-Course-Introduction/Report-Contents.md)期末的技術深度原則，沒做這些項目不會扣分；做了要能在訪談時說明。

## 四、常見的不一致與怎麼抓 🔵 期末必讀

追溯的實際作用是抓出不一致。以下六種是課程報告中最常出現的，每一種都有明確的檢查方法。

### 4.1 六種不一致 🔵 期末必讀

| 症狀 | 怎麼抓 | 代表什麼 |
|---|---|---|
| 使用案例上有的角色，流程圖上沒有 | 比對兩張圖的角色清單 | 流程漏了一種人的走法 |
| 畫面上有欄位，資料字典裡找不到 | 逐欄對照表 | 資料模型漏了，或欄位不該存在 |
| 資料字典有欄位，沒有任何畫面輸入它 | 反向對照 | 這份資料永遠是空的 |
| 狀態值在三個地方講法不同 | 抄出活動圖、畫面、資料字典的狀態文字並排 | 最常見，也最容易修 |
| 模組相依關係與循序圖的呼叫順序矛盾 | 比對模組圖的箭頭與循序圖的訊息方向 | 模組劃分或流程有一邊想錯了 |
| 風險分析提到的設計，前面章節沒有 | 逐條檢查風險的「對設計的影響」 | 風險分析是事後補的 |

### 4.2 狀態值那一條要特別花時間 🔵 期末必讀

第四種在幾乎每一份報告裡都會出現，因為狀態文字散落在太多地方：活動圖的判斷節點寫「確認通過」、畫面上的標籤顯示「已確認」、資料字典的值域寫 `20`、循序圖的訊息寫「確認來訪」。

**修法很機械**：把資料字典的值域抄出來當作唯一標準，其他三處全部改成一致。花二十分鐘，可以避免訪談時被問到「你們這個『審核通過』在資料表裡是哪個值」而答不出來。

### 4.3 交叉檢查表 🔵 期末必讀

前面各章各自給了自己的檢查清單，這裡把它們整合成交件前跑一遍的總表：

| 檢查 | 出自 |
|---|---|
| 使用案例圖的參與者，都在利害關係人清單裡 | 使用者分析 |
| 每條 Must have 需求，都找得到承接它的功能 | 功能分析 |
| 每個模組，都對應得到至少一條需求 | 功能分析 |
| 每份資料儲存，都有功能負責建立與維護 | 功能分析、資料建模 |
| 活動圖的每個例外分支，都對應到使用案例的例外流程 | 行為建模 |
| 活動圖的每個判斷節點，都對應得到一條需求或一條規則 | 需求分析、行為建模 |
| 循序圖上的每條生命線，都在模組清單裡找得到 | 功能分析、行為建模 |
| 循序圖訊息的參數，都能在畫面上找到輸入處 | 行為建模、介面設計 |
| ERD 的實體都在 Schema 找得到表，每一欄都在字典裡有定義 | 資料建模 |
| 概念類別圖上沒有落到資料表的概念，都說明了它去了哪裡 | 物件建模、資料建模 |
| 狀態機圖的每個狀態，都在資料表的值域裡 | 行為建模、資料建模 |
| 狀態機圖的每一條轉移，都有一個模組負責觸發 | 功能分析、行為建模 |
| 架構圖的每個外部系統，都有對應的介面規格，且每條介接都寫了失敗處理 | 架構、系統介面 |
| **畫面上的每一個數字，不是在資料字典裡，就是在推導欄位清單裡** | 資料建模、介面設計 |
| 每條風險，都指得回一個設計決策，也寫得出對設計的影響 | 可行性與風險 |

粗體那一條是漏得最徹底的一種。在廠人數、停留時間、某張訪客證可不可發，這些值在資料表裡通常都不存在，如果報告裡沒有一張推導欄位清單接住它們，**它們在文件上就是憑空出現的數字**，而訪談時只要問一句「這個『在廠 7 人』是怎麼算出來的、隨行的人算不算」就會露餡。

**這張表跑一遍通常要一到兩小時。** 這是交件前投資報酬率最高的一段時間，因為它抓出的每一處，都是訪談時會被問到的地方。

## 五、設計決策要留下紀錄 🔵 期末必讀

### 5.1 記錄的是理由，不是結果 🔵 期末必讀

規格書上寫「本系統採用三層式架構」只記錄了結果。三年後接手的人真正需要知道的是：**為什麼不是別的？當時考慮過什麼？**

一則設計決策紀錄包含四個部分：

> **決策**：在廠訪客名單每 15 分鐘自動輸出一份到櫃台電腦的本機檔案，可直接列印。
> **背景**：大門櫃台沒有不斷電系統，而最需要這份名單的時刻（停電、火災、疏散）正好是系統可能不能用的時刻。
> **考慮過的方案**：（一）替櫃台加裝不斷電系統，成本約 3 萬且仍撐不過長時間停電；（二）名單改放雲端，但斷網時一樣拿不到；（三）定時輸出到本機檔案。
> **選擇理由**：方案三不需額外硬體投資，而且它不依賴應用系統本身還活著。
> **代價**：那份名單最多會舊 15 分鐘，剛報到的訪客可能不在上面，此殘餘風險已登記於 R-03；架構上因此多出一條寫到櫃台本機的路徑。

**「考慮過的方案」那一段是價值所在。** 它證明這個決定是比較之後的結果，不是隨手選的；也讓後人在條件改變時（例如網路升級了）知道可以回頭檢討這個決定。

**「代價」那一段不能省，而且不要跟理由寫在一起。** 只寫理由的決策紀錄讀起來像在辯護，寫出代價才看得出你知道自己換掉了什麼。**兩則結論相反的決策放在一起看，最能證明你不是在套規則**——同樣是「算出來的東西該不該存」，一個決定不存、一個決定存，只要兩邊的理由都回到同一條判準，那就是判斷；只寫結論不寫判準，接手的人只會覺得這份設計前後不一致。

### 5.2 哪些決定值得記錄 🔵 期末必讀

不必每個決定都記。判準與[「系統環境與架構」](08-System-Architecture.md)〈一、1.2〉的架構決策相同：**難改、影響全局的才記。**

值得記錄的通常是這幾類：架構選型、資料模型的重要取捨（例如刻意不正規化）、模組怎麼切、與外部系統的介接方式、明顯的範圍取捨（哪些功能這次不做）。

### 5.3 待解問題也要寫 🔵 期末必讀

規格書結尾要有一節列出尚未解決的問題，每條寫明：問題是什麼、卡在哪裡、需要誰決定、什麼時候之前要有答案。

> **待解 O-01**：資訊部門是否同意開放一個對外的網頁入口供訪客填寫申請，尚未取得確認。若不開放，訪客必須到現場才填得了申請，事前確認的機制等於失效，第 1 項的整條流程與 UI-01 都要重寫。需於開發啟動前確認。

寫下待解問題不會扣分，**假裝它們不存在才會**——因為訪談時只要問到那個地方，就會暴露出來。

## 六、文件版本與交付

### 6.1 版本紀錄

多人協作的文件一定要有版本紀錄，至少記：版本編號、日期、改了什麼、誰改的。

這件事在課程報告中的實際用途是：**個人報告要交的「貢獻證據」，版本紀錄是最直接的一種**。這與[「分組規範」](../00-Course-Introduction/Group-Rules.md)建議保留的分工佐證是同一批東西。

### 6.2 交付的形式

期末報告的檔案格式、命名與上傳方式，一律見[「報告規範」](../00-Course-Introduction/Report-Rules.md)。本章只提醒一件與內容有關的事：**圖要看得清楚**。

一張縮到看不見文字的架構圖，等於沒交。圖太大就分張畫、或另附大圖檔；用截圖的話確認解析度足夠。訪談時老師會請你解讀自己的圖，圖上的字看不清楚，第一個吃虧的是你。

## 七、交件前的最後一輪 🔵 期末必讀

把前面的內容收成一份可以直接執行的清單。**交件前一天做這九件事**：

1. 跑一遍〈四、4.3〉的交叉檢查表，記下所有對不上的地方。
2. 挑三到五條關鍵需求，各走完一次五段追溯鏈，走不通的表示中間有斷點。
3. **拿一條非功能需求追一次到底。** 大多數組別只追得動功能需求，非功能需求追不動的地方，就是設計的破口。
4. **追溯矩陣由右往左也掃一次**，找出不對應任何需求的模組、資料表與畫面。
5. 把狀態值在四個地方的寫法抄出來並排，統一成資料字典的版本。
6. 檢查每張圖上的文字看不看得清楚。
7. 確認每個可選項目都列進了額外項目對照表（見[「報告內容」](../00-Course-Introduction/Report-Contents.md)）。
8. 把還沒解決的問題寫成待解清單，不要留白。
9. 找一位沒有寫這一段的組員讀一次，問他有沒有看不懂的地方。

**最後一項最有效也最少人做。** 自己寫的東西自己看永遠是通順的；換一個人讀，五分鐘就能找出你完全沒察覺的跳躍。

做完這九件事，最後問自己一個總結性的問題：**只拿這份文件，別人做得出這套系統嗎？** 期中的判準是「你看懂了沒有」，期末的判準是「別人照著做得出來嗎」。整份文件裡如果有一段連你自己都答不出「照這樣寫會做出什麼」，那一段就還沒完成——而那幾段，正是資訊人員接手後第一個回頭來問你的地方。

## 八、學習重點總結

讀完本章後，你應該能夠理解以下核心概念，並將其應用於工業場域的思考與決策：

**一疊文件不等於一套設計**

規格書的價值不在收錄了什麼，而在證明各份文件講的是同一套系統、每項設計都追溯得回某個需求、任何人接手都看得懂為什麼要這樣做。裝訂起來交出去，讀者仍無法判斷這些東西彼此對不對得起來——而那正是評分時在看的東西。

**追溯鏈的空格是有意義的**

需求到模組到流程到資料到畫面，五段走完才算完整。某一段接不上，不是文件格式的問題，是設計本身有斷點：一條需求找不到承接的模組，代表它沒被實作；一份資料沒有任何畫面輸入，代表它永遠是空的。追溯表上的空格逼你回答這些問題。

**同一件事在五個地方講法要一致**

狀態值散落在活動圖、畫面、資料字典與循序圖裡，四處寫法不同是幾乎每份報告都會出現的問題。修法很機械：以資料字典的值域為準，其他三處全部改齊。二十分鐘的工作，可以避免訪談時被問到「這個狀態在資料表裡是哪個值」而答不出來。

**記錄理由比記錄結果重要**

「本系統採用三層式架構」只是結果。接手維護的人真正需要知道的是當時考慮過哪些方案、為什麼選這個、代價是什麼。一套系統的維護期遠比開發期長，看不懂當初理由的人只能猜，而猜錯的代價是改壞既有功能。

**待解問題要寫出來**

一份標示了「這三件事尚待確認」的規格，比一份每個角落都填滿的規格可信得多。假裝問題不存在不會讓它消失，只會在訪談被問到那個地方時暴露出來。分得清「已確認的」與「還沒確認的」，是專業程度最直接的指標。

**找一個沒寫這段的人讀一次**

自己寫的東西自己讀永遠通順，因為你腦中補齊了文件上沒寫的部分。換一個人讀五分鐘，就能找出你完全沒察覺的跳躍與斷點。這是交件前投資報酬率最高的一件事，也是最少人做的一件事。
