# 系統介面與資料交換設計

工廠裡幾乎沒有一套系統是獨立運作的。ERP 把生產工單下給現場系統，現場系統把實際產出回報給 ERP，倉儲系統依生產進度準備物料，品管系統要拿到每批的檢驗結果。這些系統各自都有人維護、各自都運作正常，但 **出問題的地方往往在它們之間**。

原因很單純：每一套系統內部都有明確的負責人，而兩套系統之間那條線通常沒有。工單今天沒下來，現場說「ERP 沒給」，資訊部說「我們有送」，誰也拿不出證據。等到查清楚是格式改了沒通知，已經停線兩小時。

本章要處理的就是那條線。**核心不是學會寫程式串接，而是把交換講清楚：誰給誰、給什麼、什麼時候給、給失敗了怎麼辦。** 這四件事說得清楚，介接就有人負責；說不清楚，再厲害的技術也擋不住互相推諉。

期末報告不要求寫完整的介面規格。依[「報告內容」](../00-Course-Introduction/Report-Contents.md)期末第 11 項，**修改方向涉及資料匯出或匯入時**，要寫出檔案的欄位與格式，寫法見〈八〉，會用到〈三〉的五件事與〈五、5.1〉的 CSV。

期中也是條件式的，而且列為可選。課堂範例系統沒有任何對外介接，所以那份範例報告不做這一項；但你抽到的題目若有外部系統或現場設備，可以在期中第 5 項標出交界在哪一段，不必寫到本章〈三〉那種完整的介面規格。反過來說，**確認過沒有外部介接，也要在報告裡寫一句話交代**，不要留白讓人以為是漏了——寫法見[「功能分析」](05-Functional-Analysis.md)〈二、2.3〉。

> **前情提要**：本章假設你已完成[「系統環境與架構」](08-System-Architecture.md)的架構圖——那張圖標出了哪些系統相連，本章接著處理它們之間實際交換什麼。本章沿用期末示範的訪客系統修改版 `SAD-Visitor-Revised`。這套系統現況沒有任何對外介接，員工名單由管理員手動維護，見[「期末範例報告」](../04-Final-Project-Example-Reports/Final-Phase-Sample-Report.md)〈3.4〉；修改後由系統產出、交到系統之外的資料只有一項，就是 CR-03-2 匯出的當日訪客總覽 CSV。與人資系統同步仍在系統邊界之外，本章只在說明需要時，以「如果要納入系統」的方式帶到。

> **延伸閱讀**：完整的 REST API 規格（HTTP 方法、狀態碼、Endpoint、Request／Response）在本課程列為可選項目，見〈六〉。

> **期末必讀標記**：標題後加註 🔵 期末必讀 的小節，是期末報告直接會用到的內容。判準與成品的樣子見[「期末範例報告」](../04-Final-Project-Example-Reports/Final-Phase-Sample-Report.md)。未標記的小節仍屬課程範圍，只是期末不會直接產出。

## 一、什麼是系統介面

### 1.1 介面是一份約定

**系統介面（Interface）是兩套系統之間關於「怎麼傳資料」的約定。** 它像兩個部門之間的交接規則：誰在什麼時候把什麼東西交給誰、格式長什麼樣、對方要回什麼、東西沒收到怎麼辦。

這個類比不是比喻而已。工廠裡的物料交接如果沒有明確規則，就會出現「我以為你會來拿」「我放在那邊了你沒看到」的爭議；系統介接沒有明確規則，出現的是同一類問題，只是換成資料。

### 1.2 為什麼介面特別容易出事

| 原因 | 具體情況 |
|---|---|
| 沒有單一負責人 | 兩邊的維護團隊都認為對方該負責 |
| 改動不會互相通知 | ERP 升級改了欄位，沒人告訴現場系統的維護者 |
| 失敗不會馬上被發現 | 資料沒傳過來，可能要到隔天對帳才知道 |
| 測試困難 | 要兩邊都準備好才測得起來，通常留到最後 |

**第三項是最麻煩的。** 一個畫面壞掉，使用者立刻會反映；一條介接靜靜地失敗，可能累積幾天才被發現，而那時要補的資料已經是一大批。這也是為什麼〈三〉的失敗處理是介面規格裡最不能省的一段。

## 二、從流程找出交換點

### 2.1 交換點在哪裡

不必憑空想像哪裡需要介接，回頭看你畫過的圖就找得到：

**看架構圖。** [「系統環境與架構」](08-System-Architecture.md)〈三〉那張圖上，每一條連到外部系統或現場設備的箭頭，就是一個交換點。

**看流程圖。** 活動圖上如果有一個動作的輸入不是來自本系統的使用者，那份資料一定是從別處來的。範例的來訪登記流程中，系統會顯示受訪員工的分機，讓接待員打分機通知（範例〈2.1〉）；這份資料如果不是本系統建立的，就是介接來的。範例的分機是管理員在 UI-07 員工名單頁輸入的，所以不算交換點。

**看資料模型。** 資料字典的「來源」那一欄如果寫著某個外部系統，那就是一個交換點。這也是[「資料建模與資料庫設計」](07-Data-Modeling.md)〈五、5.1〉要求填那一欄的用意之一。範例〈4.4〉的 `employees` 每一欄的來源都是「管理員輸入」「管理員切換」或「系統產生」，沒有一欄來自外部系統，這也是範例〈3.4〉寫得出「系統沒有任何外部系統或設備介接」的依據之一。

### 2.2 訪客登記系統的交換點

修改後的訪客系統，資料跨出系統的地方有兩處，一處由系統產出，一處仍由人工處理：

| 方向 | 交換什麼 | 現在怎麼做 |
|---|---|---|
| 訪客登記系統 → 管理員留存、交給主管 | 當日訪客總覽，一人一列 | CR-03-2 新增：管理員在 UI-12 當日訪客總覽按「匯出 CSV」下載檔案（範例〈11.3〉） |
| 人資部 → 訪客登記系統 | 需要開帳號的員工名單、員工離職的通知 | 在系統之外：人資部提供名單、員工離職時通知管理員，管理員在 UI-07 員工名單頁與 UI-09 帳號管理頁手動維護（範例〈13.1〉） |

第一條是〈八〉要處理的期末匯出檔。它的另一端是人，不是另一套系統，但給什麼、什麼時候給、失敗了怎麼辦，一樣要寫清楚。

第二條目前不是系統介面，是兩個部門之間的人工交接，範例〈3.4〉把「與人資系統同步」列在系統邊界之外。**如果要把與人資系統同步納入系統，這條線就變成系統對系統的交換點**，〈三〉的五件事都要寫出來，第一個要決定的是誰主動。

**推（Push）與拉（Pull）是兩種不同的設計**：人資系統主動把名單推過來，或訪客登記系統定時去人資撈。兩者的差別在於出問題時誰負責察覺——推的話人資要確認送達，拉的話訪客登記系統要確認撈到。員工名單適合用拉：時效不敏感，主動權在自己手上，對方不必為你改任何東西。範例的 CSV 匯出也是拉：管理員要的時候自己按，系統不會主動送出。

## 三、一份介面規格要交代什麼 🔵 期末必讀

這是本章的核心。**每一個交換點，都要把下面五件事各寫一次。** 期末的匯出檔是只有一個方向的交換，同樣適用，見〈八〉。

### 3.1 五件事 🔵 期末必讀

| 項目 | 要回答 |
|---|---|
| 資料來源 | 這份資料從哪個系統、哪張表、哪個欄位來 |
| 資料去向 | 送到哪個系統、存進哪裡 |
| 交換內容 | 有哪些欄位、各是什麼意思、必填還是選填 |
| 交換時機或頻率 | 什麼時候傳、多久一次、由誰觸發 |
| 失敗處理 | 傳不過去怎麼辦、誰會知道、怎麼補 |

### 3.2 交換內容要逐欄列出

只寫「匯出當日訪客總覽」不夠，要列出欄位。期末的匯出檔只有本系統這一邊，列出檔案有哪些欄位即可（見〈八〉）。但檔案的欄位和資料表的欄位往往不是同一回事，要逐欄對照、標明轉換規則才看得出差別。範例〈11.3〉的 CSV 欄位對回 `SAD-Visitor-Revised` 的資料表，是這樣（依系統的匯出程式整理，節錄六欄）：

| CSV 欄位 | 資料表的欄位 | 轉換規則 |
|---|---|---|
| 狀態 | `appointments.status`、`visit_date`，`visits.check_in_at`、`check_out_at` | 資料表沒有這一欄，依 BR-08 推導成五種文字之一 |
| 類別 | 無 | 訪客那一列寫「訪客」；`visit_companions` 的每一筆各占一列，寫「隨行」 |
| 姓名 | 預約列取 `appointments.visitor_name`，來訪列取 `visitors.name`，隨行列取 `visit_companions.name` | 同一欄依列的種類取不同的表 |
| 受訪員工 | `appointments.employee_id` 或 `visits.employee_id` 對應的 `employees.name` | 資料表存編號，檔案裡換成姓名 |
| 訪客證 | `visits.pass_id` 對應的 `visitor_passes.pass_no` | 資料表存編號，檔案裡換成證號，例如 `V-03` |
| 報到時間 | `visits.check_in_at` | 照原格式 `YYYY-MM-DD HH:MM:SS` 輸出；預約列留空 |

兩套系統互相介接時也是同一張表，只是左欄換成對方系統的欄位。

**「轉換規則」那一欄是實務上最容易出事的地方**，尤其是單位、時區、日期格式與值域的對應。一個把公斤當公克的介接，帳面上每天都正常運作，但數字全錯。

上表的「狀態」示範另一種常見的狀況：**兩邊的值域顆粒度不同**。資料庫裡的預約有已預約、已報到、已取消三個值，檔案裡卻沒有「已報到」：範例在〈5.3〉決定已報到的預約只以來訪列出一次，否則同一個人會算兩次。這是一項業務決定，不是技術決定。如果要與人資系統同步，同樣的問題會出在在職狀態：`employees.is_active` 只有在職、離職兩個值，人資若另有留職停薪，它要歸到哪一邊——留職停薪的人能不能被選為受訪員工——要先有人決定。

### 3.3 時機與頻率有三種

| 型態 | 意思 | 適合的情況 |
|---|---|---|
| 即時 | 事件一發生就傳 | 時效要求高，例如 ERP 一下工單，現場系統就要看得到 |
| 批次 | 固定時間一次傳一批 | 資料量大、時效要求低，例如每天同步一次員工名單 |
| 人工觸發 | 由人按下按鈕才傳 | 頻率低或需要人為確認，例如範例的 CSV 匯出 |

選擇的判準是 **對方多快需要這份資料**。學生常直覺選「即時」，但即時介接的維護成本高得多，它要求兩邊系統隨時都在線上。範例的總覽是管理員下班前匯出留存、主管臨時要看時才匯出（範例〈11.3〉），人工觸發就夠。如果要與人資系統同步，員工名單一天一次也夠：新進員工的資料晚一天出現，管理員在員工名單頁手動補一筆就繞過去了。

### 3.4 失敗處理是最不能省的一段

至少要回答三個問題：

**傳不過去時，資料會怎樣？** 丟掉、留在原地重試、還是存到待處理區？多數情況應該是後兩者，丟掉的資料沒有人補得回來。

**誰會知道失敗了？** 一定要有人。可以是系統發通知給資訊人員、可以是在畫面上顯示「最後同步時間」讓使用者自己察覺。**沒有任何人會知道的失敗，是最糟的設計。**

**怎麼補？** 自動重試幾次、隔多久一次；重試仍失敗時由誰手動處理。

以範例的 CSV 匯出回答這三題：

| 問題 | 範例的 CSV 匯出 | 依據 |
|---|---|---|
| 資料會怎樣 | 匯出只讀取資料，失敗不會改動任何紀錄，重按一次即可 | 範例〈7.3〉 |
| 誰會知道 | 按下匯出的管理員，沒拿到檔案當場就知道 | 人工觸發（本章〈3.3〉） |
| 怎麼補 | 改用瀏覽器列印總覽頁；總覽頁本身也出錯時，管理員先用來訪紀錄查詢與在廠清單整理名單，大門的登記與離廠不受影響 | 範例〈11.3〉〈15.3〉 |

人工觸發的交換，「誰會知道」這題幾乎自動有答案。**排程自動執行的批次就不是這樣**：如果要與人資系統同步，半夜同步失敗時旁邊沒有人，就要另外設計——保留上一次成功取得的名單繼續運作、在畫面上顯示最後同步時間、連續失敗時通知資訊人員。

這幾句話沒有任何程式碼，但已經把責任、時機與補救講清楚。期末匯出檔的失敗處理寫到這個深度就夠了，見〈八、8.1〉。

## 四、交換的三種技術做法

技術做法有很多種，對本課程而言認得三類就夠。

| 做法 | 怎麼運作 | 特點 |
|---|---|---|
| 檔案交換 | 一邊產出檔案放到共用位置，另一邊定時去讀 | 最簡單、最老派，但很可靠；適合批次 |
| 資料庫交換 | 一邊直接讀寫另一邊的資料庫或中介資料表 | 快，但兩邊綁太緊，一方改結構另一方就壞 |
| [Web 服務](https://zh.wikipedia.org/wiki/Web服务) | 一邊提供網路介面，另一邊呼叫它 | 目前主流，適合即時；需要雙方都能連上網路 |

**選哪一種不完全是技術決定，多半取決於對方系統開放到什麼程度。** 套裝的人資系統常常只開放固定格式的檔案匯出，那就只能用檔案交換——這一點在[「效益評估與上線準備」](10-Benefit-and-Go-Live.md)〈六〉屬於既有系統的限制。

期末的匯出檔屬於檔案交換：系統產出檔案，交給人或另一套系統讀。報告寫清楚檔案長什麼樣即可，不必寫實作細節。

## 五、資料格式 🔵 期末必讀

### 5.1 CSV 🔵 期末必讀

[逗號分隔值](https://zh.wikipedia.org/wiki/逗号分隔值)（CSV）是最單純的表格式格式，一行一筆、逗號分欄。

以 `SAD-Visitor-Revised` 的種子資料為例，把「今天」當成 2026-11-04，當日訪客總覽匯出的 CSV 是下面這樣。第一行是欄位名稱，之後每一行是一個人：

```
"狀態","類別","姓名","公司","手機","受訪員工","部門","分機","預計到達時間","報到時間","離廠時間","訪客證"
"在廠（非今日報到）","訪客","陳俊宏","永協機電","0933555666","鄭大偉","設備課","2401","","2026-11-02 13:30:00","","V-03"
"在廠（非今日報到）","隨行","（未記錄姓名，共 1 人）","永協機電","","鄭大偉","設備課","2401","","2026-11-02 13:30:00","","V-03"
"在廠","訪客","張家豪","宏昇精密","0911888999","李志明","生產部","2101","","2026-11-04 08:55:00","","V-05"
"在廠","訪客","蔡宗翰","德鑫自動化","0977222333","鄭大偉","設備課","2401","09:00","2026-11-04 09:10:00","","V-06"
"已離廠","訪客","林淑芬","順安物流","0922333444","吳建國","採購部","2301","","2026-11-04 09:30:00","2026-11-04 09:50:00","V-02"
"預約中","訪客","周志強","冠宇科技","0918222333","李志明","生產部","2101","10:00","","",""
"已取消","訪客","吳佩珊","和泰工程","0928444555","鄭大偉","設備課","2401","14:00","","",""
```

系統把每一格都用雙引號包起來，內容裡就算有逗號，也不會被切成兩欄。

優點是任何人都能用 Excel 打開檢查，適合批次交換。缺點是表達不了層次結構：陳俊宏和他的隨行人員是一對多，用 CSV 只能拆成兩個檔案，或像上面這樣攤平成多列、重複所屬訪客的欄位（範例為什麼選攤平，見本章〈8.2〉）。

### 5.2 JSON

[JSON](https://zh.wikipedia.org/wiki/JSON) 用大括號與中括號表達結構，可以有層次。修改後的訪客系統，畫面與伺服器之間就是用 JSON 交換資料。照範例的 TC-15 在來訪登記頁登記種子資料裡的張家豪（手機 `0912345678`），並輸入兩位隨行人員時，畫面送給伺服器的內容長這樣（兩個隨行人員姓名是測試時自己填的）：

```json
{
  "employee_id": "1",
  "purpose": "開會",
  "companion_names": ["王志成", "林雅惠"],
  "plate_no": "",
  "note": "",
  "pass_id": "1",
  "visitor_id": 1
}
```

看不懂符號沒關係，**要看的是它表達了什麼**：一筆來訪登記有受訪員工、事由、車牌、備註、訪客證與訪客六個欄位，加上一個隨行人員清單，清單裡有兩個人。伺服器收到後在 `visits` 寫一筆、在 `visit_companions` 寫兩筆，隨行人數記為 2（FR-07）。這種一對多的結構，一份 JSON 就裝得下，CSV 做不到。

另外注意 `employee_id` 與 `pass_id` 傳的是編號（前者的 `1` 是李志明，後者的 `1` 是 `V-01`），不是姓名與證號。畫面與伺服器屬於同一套系統，共用同一個資料庫的編號；交到系統之外的 CSV，才要換成姓名與證號（本章〈3.2〉）。

### 5.3 欄位命名要一致

不論用哪種格式，同一件事在整個系統裡要用同一個名稱。`visit_no`、`visitNo`、`v_no` 混用，會讓每一次介接都要多一層對照。

**這一點與[「資料建模與資料庫設計」](07-Data-Modeling.md)的資料字典是同一件事**：字典裡定義過的欄位名稱，介面規格直接沿用，不要另創一套。

## 六、REST API（進階閱讀）

以下屬於可選內容。**不做不扣分**，但這幾個名詞在業界討論中一定會遇到，值得認得。

### 6.1 基本概念

[REST](https://zh.wikipedia.org/wiki/REST) 是目前最普遍的 Web 服務風格，它的想法是把系統裡的東西當成「資源」，用[網路傳輸協定](https://zh.wikipedia.org/wiki/超文本传输协议)本身的動詞來操作。

修改後的訪客系統，畫面向伺服器要資料、送資料，就是用這種寫法。這套網路介面只給自己的畫面用，不是對外介接，但寫法相同：

| 動詞 | 意思 | 修改後訪客系統的例子 |
|---|---|---|
| GET | 取得 | `GET /api/visits/7`：取得編號 7 的來訪明細（UI-05） |
| POST | 新增 | `POST /api/visits`：登記一筆來訪（UI-03） |
| PUT | 更新 | `PUT /api/visits/7`：修改這筆來訪的事由、受訪員工、隨行人員姓名等（FR-14） |
| DELETE | 刪除 | 沒有。來訪紀錄不得刪除（NFR-04）；取消預約也不刪資料，而是用 `POST /api/my/appointments/{預約編號}/cancel` 把狀態改成已取消 |

每個資源有一個網址，例如 `/api/visits/7` 代表編號 7 的來訪紀錄。呼叫之後伺服器會回一個狀態碼說明結果，修改後的系統用到這幾個：`200` 成功、`400` 輸入有誤（例如「請選擇訪客證」）、`401` 還沒登入、`403` 這個帳號沒有權限（接待員直接呼叫匯出功能時就回這個，範例的 TC-17 驗的就是它）、`404` 找不到、`500` 系統出錯。

### 6.2 完整規格會寫什麼

一份完整的 API 規格，每個端點都要寫出網址、動詞、輸入參數、成功與失敗的回應內容，以及[身分驗證](https://zh.wikipedia.org/wiki/身份验证)方式。

**這在本課程列為可選。** 選擇做的話，要能在訪談時說明每個設計決定：為什麼這個操作用 POST 不用 PUT、取消預約為什麼不用 DELETE、為什麼回這個狀態碼。做了卻講不出來，比不做更糟。

### 6.3 不做也要能回答的問題

即使不寫 API 規格，期末訪談仍可能問到：「這個外部系統和你們的系統交換哪些資料？」這個問題要回答的是〈三〉那五件事，與有沒有寫 API 規格無關。**五件事說得清楚，就達到本課程的要求了。**

## 七、介面與其他文件的對照

介面規格寫完之後，與前面各章交叉檢查：

| 對照 | 檢查什麼 | 對不上代表 |
|---|---|---|
| 介面 → 架構圖（只適用期中） | 每一條介接在架構圖上都有對應的連線 | 架構圖漏了一個外部系統 |
| 介面 → 資料字典 | 交換的每個欄位都在資料字典裡找得到 | 資料模型漏了欄位，或介接了用不到的資料 |
| 介面 → 流程圖 | 交換的時機在流程圖上有對應的觸發點 | 沒想清楚這份資料什麼時候該進來 |
| 介面 → 失敗處理 | 每條介接都寫了失敗怎麼辦 | 最常見的遺漏 |

最後一條是介面規格裡最常被跳過的一段。**學生描述介接時，幾乎都只寫順利的情況**——這與[「行為建模」](06-Behavioral-Modeling.md)〈三〉活動圖只畫順利路徑是同一種毛病。

## 八、期末：匯出檔的欄位與格式 🔵 期末必讀

期末示範的訪客系統沒有對外介接，資料交換出現在修改方向裡：CR-03 要求把當日訪客總覽匯出成 CSV，讓管理員留存。五題之中，教育訓練題的修改需求提案書也有匯出 CSV 的要求。依期末第 11 項，這類修改要寫出檔案的欄位與格式。

匯出檔是只有一個方向的交換，〈三〉的五件事照樣適用，另外再交代幾件檔案特有的事。匯入檔也一樣，只是方向反過來：來源是檔案，去向是系統的資料表，失敗處理要回答格式不對的那幾列怎麼辦。

### 8.1 用五件事檢查匯出檔 🔵 期末必讀

以[「期末範例報告」](../04-Final-Project-Example-Reports/Final-Phase-Sample-Report.md)的 CR-03-2 當日訪客總覽為例：

| 五件事 | 範例的寫法 | 寫在範例的哪裡 |
|---|---|---|
| 資料來源 | 今天的預約與今天相關的來訪紀錄，連同訪客、受訪員工、訪客證與隨行人員，共讀取六張表 | 〈16.3〉 |
| 資料去向 | 管理員留存，主管要看當日狀況時交給主管 | 〈11.3〉 |
| 交換內容 | 狀態、類別（訪客／隨行）、姓名、公司、手機、受訪員工、部門、分機、預計到達時間、報到時間、離廠時間、訪客證 | 〈11.3〉 |
| 時機 | 由管理員按鈕匯出（人工觸發）：每天下班前一次，主管臨時要看時隨時匯出 | 〈11.3〉 |
| 失敗處理 | 改用瀏覽器列印總覽頁 | 〈11.3〉 |

**失敗處理要看這份檔案多急。** 當日訪客總覽是留存用的，匯出失敗時印一份紙本就夠了。如果檔案是緊急時要用的，例如疏散時的點名名單，伺服器當下不一定連得上，答案就不能只是「重試」或「列印」，要平常就先留一份檔案。

### 8.2 檔案格式要多交代的事 🔵 期末必讀

| 項目 | 為什麼要寫 | 範例的寫法 |
|---|---|---|
| 檔名 | 一天可能匯出好幾次，要分得出哪一份最新 | `當日訪客總覽_YYYYMMDD_HHMM.csv`，時間為匯出當下 |
| 編碼 | 中文用 Excel 直接開啟可能變成亂碼 | UTF-8，含 BOM，並寫成非功能需求 NFR-08 |
| 每一列代表什麼 | 一對多的資料要決定怎麼攤平 | 一列一個人：訪客一列，每位隨行人員各一列 |
| 特殊情況 | 舊資料或缺值時，檔案裡要寫什麼 | 舊紀錄只有隨行人數，就寫一列，姓名寫「（未記錄姓名，共 N 人）」 |

[UTF-8](https://zh.wikipedia.org/wiki/UTF-8) 是一種文字編碼，也就是把文字存成電腦檔案的規則。BOM（Byte Order Mark）是放在檔案最前面的一個標記，Excel 看到它才知道要用 UTF-8 讀，中文才不會亂碼。

「每一列代表什麼」要特別想。〈5.1〉提到 CSV 表達不了一對多，給另一套系統讀的檔案可以拆成兩個檔；當日訪客總覽是給人看的，範例改成一人一列，用「類別」欄分出訪客與隨行人員，隨行人員那幾列重複所屬訪客的狀態、公司、受訪員工與訪客證，看的人不必再對照另一個檔案。

「特殊情況」那一列要和第 14 項的資料轉換規則一致：範例在〈14.3〉決定舊紀錄只保留人數、不補姓名，CSV 就照這個決定寫。

這張格式表也是驗收的依據。範例的 TC-14 照著它檢查檔名、中文會不會亂碼、舊紀錄那一列對不對，追溯表的「畫面」欄也指到〈11.3〉的 CSV 格式，見[「系統設計規格與追溯」](13-Design-Specification.md)〈三、3.4〉。

抽到教育訓練題的組別，提案書〈3.4 待小組決議的問題〉也問了 CSV 要有哪些欄位、多久匯出一次、交給誰。這幾題沒有標準答案，用本節的兩張表逐項決定，在第 5 項寫出決議與理由，不要照抄範例的欄位。修改方向沒有匯出或匯入的題目，第 11 項的這一條不必寫。

## 九、學習重點總結

讀完本章後，你應該能夠理解以下核心概念，並將其應用於工業場域的思考與決策：

**介面是約定，不是技術**

兩套系統之間出問題，多半不是因為技術做不到，而是因為沒有人講清楚誰給誰、給什麼、什麼時候給、失敗了怎麼辦。這四件事與工廠裡的物料交接規則是同一種東西——沒有明確約定，就會出現「我以為你會來拿」的爭議，只是換成資料。

**介接的失敗特別難察覺**

畫面壞掉使用者立刻會反映，一條介接靜靜地失敗卻可能累積好幾天才被發現。所以失敗處理是介面規格裡最不能省的一段，而其中最關鍵的問題是「誰會知道失敗了」。沒有任何人會知道的失敗，是最糟的設計。

**轉換規則是實務上最常出事的地方**

兩套系統對同一件事的欄位名稱、單位、日期格式往往不同；就算只是把資料匯出給人看，資料表裡存的編號與代碼也要換成姓名與文字。一個把公斤當公克的介接，帳面上每天都正常運作但數字全錯，而且很難被發現。逐欄列出對應關係與轉換規則，是介面規格裡最枯燥卻最有價值的一段。

**即時不是預設值**

即時介接要求兩邊系統隨時在線，維護成本比批次高得多。選擇的判準是對方多快需要這份資料——範例的當日訪客總覽是下班前留存用的，由管理員按鈕匯出就夠；如果要與人資系統同步，員工名單一天一次也夠。直覺選即時，通常代表沒有想過代價。

**技術做法多半由對方決定**

檔案交換、資料庫交換、Web 服務三種做法，選哪一種往往取決於對方系統開放到什麼程度，而不是你的偏好。套裝 ERP 只開放固定格式的檔案匯出時，你就只能用檔案交換，這在可行性分析裡屬於既有系統的限制。

**說清楚五件事就達到要求了**

資料來源、去向、內容、時機、失敗處理。這五件事寫得清楚，不需要一行程式碼、不需要 API 規格，介接就有人負責、出事就查得到。期末的匯出檔也用這五件事檢查，再補上檔名、編碼與一列代表什麼。REST 與完整規格是可選內容，做了要能說明，說不出來反而扣分。
