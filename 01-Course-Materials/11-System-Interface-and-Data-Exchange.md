# 系統介面與資料交換設計

工廠裡幾乎沒有一套系統是獨立運作的。ERP 把生產工單下給現場系統，現場系統把實際產出回報給 ERP，倉儲系統依生產進度準備物料，品管系統要拿到每批的檢驗結果。這些系統各自都有人維護、各自都運作正常，但 **出問題的地方往往在它們之間**。

原因很單純：每一套系統內部都有明確的負責人，而兩套系統之間那條線通常沒有。工單今天沒下來，現場說「ERP 沒給」，資訊部說「我們有送」，誰也拿不出證據。等到查清楚是格式改了沒通知，已經停線兩小時。

本章要處理的就是那條線。**核心不是學會寫程式串接，而是把交換講清楚：誰給誰、給什麼、什麼時候給、給失敗了怎麼辦。** 這四件事說得清楚，介接就有人負責；說不清楚，再厲害的技術也擋不住互相推諉。

期末報告不要求寫完整的介面規格。依[「報告內容」](../00-Course-Introduction/Report-Contents.md)期末第 11 項，**修改方向涉及資料匯出或匯入時**，要寫出檔案的欄位與格式，寫法見〈八〉，會用到〈三〉的五件事與〈五、5.1〉的 CSV。

期中也是條件式的，只是門檻低得多。課堂範例系統沒有任何對外介接，所以那份範例報告不做這一項；但你抽到的題目若有外部系統或現場設備，期中第 5 項就必須標出交界在哪一段，只是不必寫到本章〈三〉那種完整的介面規格。反過來說，**確認過沒有外部介接，也要在報告裡寫一句話交代**，不要留白讓人以為是漏了——寫法見[「功能分析」](05-Functional-Analysis.md)〈二、2.3〉。

> **前情提要**：本章假設你已完成[「系統環境與架構」](08-System-Architecture.md)的架構圖——那張圖標出了哪些系統相連，本章接著處理它們之間實際交換什麼。本章沿用同一情境：某金屬沖壓工廠的訪客登記系統要與既有的人資系統介接，並示範它若要再往前一步、與門禁系統雙向連動時該怎麼寫。這是教學用的假設情境：期末示範的訪客系統現況沒有任何對外介接，員工名單由管理員手動維護，見[「期末範例報告」](../04-Final-Project-Example-Reports/Final-Phase-Sample-Report.md)〈3.4〉。

> **延伸閱讀**：完整的 REST API 規格（HTTP 方法、狀態碼、Endpoint、Request／Response）在本課程列為可選項目，見〈六〉。

> **期末必讀標記**：標題後加註 🔵 期末必讀 的小節，是期末報告直接會用到的內容。判準與成品的樣子見[「期末範例報告」](../04-Final-Project-Example-Reports/Final-Phase-Sample-Report.md)。未標記的小節仍屬課程範圍，只是期末不會直接產出。

## 一、什麼是系統介面

### 1.1 介面是一份約定

**系統介面（Interface）是兩套系統之間關於「怎麼傳資料」的約定。** 它像兩個部門之間的交接規則：誰在什麼時候把什麼東西交給誰、格式長什麼樣、對方要回什麼、東西沒收到怎麼辦。

這個類比不是比喻而已。工廠裡的物料交接如果沒有明確規則，就會出現「我以為你會來拿」「我放在那邊了你沒看到」的爭議；系統介接沒有明確規則，出現的是同一類問題，只是換成資料。

### 1.2 為什麼介面特別容易出事

| 原因 | 具體情況 |
|---|---|
| 沒有單一負責人 | 兩邊的維護團隊都認為對方該負責 |
| 改動不會互相通知 | ERP 升級改了欄位，沒人告訴現場系統的維護者 |
| 失敗不會馬上被發現 | 資料沒傳過來，可能要到隔天對帳才知道 |
| 測試困難 | 要兩邊都準備好才測得起來，通常留到最後 |

**第三項是最麻煩的。** 一個畫面壞掉，使用者立刻會反映；一條介接靜靜地失敗，可能累積幾天才被發現，而那時要補的資料已經是一大批。這也是為什麼〈三〉的失敗處理是介面規格裡最不能省的一段。

## 二、從流程找出交換點

### 2.1 交換點在哪裡

不必憑空想像哪裡需要介接，回頭看你畫過的圖就找得到：

**看架構圖。** [「系統環境與架構」](08-System-Architecture.md)〈三〉那張圖上，每一條連到外部系統或現場設備的箭頭，就是一個交換點。

**看流程圖。** 活動圖上如果有一個動作的輸入不是來自本系統的使用者，那份資料一定是從別處來的。「系統顯示受訪員工的部門與分機」，這些資料如果不是本系統建立的，就是介接來的。

**看資料模型。** 資料字典的「來源」那一欄如果寫著某個外部系統，那就是一個交換點。這也是[「資料建模與資料庫設計」](07-Data-Modeling.md)〈五、5.1〉要求填那一欄的用意之一。

### 2.2 訪客登記系統的交換點

訪客登記系統有一個必要的交換點，以及一個「要不要做」的選項：

| 方向 | 交換什麼 | 誰主動 |
|---|---|---|
| 人資系統 → 訪客登記系統 | 員工名單（工號、姓名、部門、分機、在職狀態） | 待決定 |
| 訪客登記系統 → 門禁系統 | 訪客證的授權（證號、可通行區域、有效時段） | 待決定 |
| 門禁系統 → 訪客登記系統 | 實際刷卡進出紀錄（證號、門位、時間） | 待決定 |

第一條是必要的：沒有員工名單，訪客就選不到受訪人。後兩條合起來構成一個雙向介接，**做了它，本章開頭那個「訪客沒登記就離廠」的問題就有解**——門禁刷卡出去時系統會知道。但它需要門禁廠商配合開放介面並改動既有設備，做不做要先評估成本。

「誰主動」這一欄是設計決定，不是既定事實。**推（Push）與拉（Pull）是兩種不同的設計**：人資系統主動把名單推過來，或訪客登記系統定時去人資撈。兩者的差別在於出問題時誰負責察覺——推的話人資要確認送達，拉的話訪客登記系統要確認撈到。

**兩個方向的選擇通常不一樣，而且理由不同。** 員工名單適合用拉：一天一次、時效不敏感，而且主動權在自己手上，對方不必為你改任何東西。訪客證授權則適合用推：訪客報到的那一刻就要能刷得開門，晚三十分鐘等於白做。**同一個介接的兩個方向各自決定推或拉，是很正常的設計，不必強求一致。**

## 三、一份介面規格要交代什麼 🔵 期末必讀

這是本章的核心。**每一個交換點，都要把下面五件事各寫一次。** 期末的匯出檔是只有一個方向的交換，同樣適用，見〈八〉。

### 3.1 五件事 🔵 期末必讀

| 項目 | 要回答 |
|---|---|
| 資料來源 | 這份資料從哪個系統、哪張表、哪個欄位來 |
| 資料去向 | 送到哪個系統、存進哪裡 |
| 交換內容 | 有哪些欄位、各是什麼意思、必填還是選填 |
| 交換時機或頻率 | 什麼時候傳、多久一次、由誰觸發 |
| 失敗處理 | 傳不過去怎麼辦、誰會知道、怎麼補 |

### 3.2 交換內容要逐欄列出 🔵 期末必讀

只寫「傳送員工資料」不夠，要列出欄位。期末的匯出檔只有本系統這一邊，列出檔案有哪些欄位即可（見〈八〉）。兩套系統互相介接時，雙方對同一件事的欄位名稱與格式往往不同，就要像下表這樣逐欄對照、標明轉換規則：

| 人資系統的欄位 | 意義 | 訪客登記系統的欄位 | 轉換規則 |
|---|---|---|---|
| `EMP_NO` | 員工編號 | `employee_id` | 直接對應 |
| `EMP_NAME` | 姓名 | `employee_name` | 直接對應 |
| `DEPT_CD` | 部門代碼 | `department` | 人資存代碼（`D14`），本系統要顯示名稱（設備課），需查對照表轉換 |
| `STATUS` | 在職狀態 | `is_employed` | 人資有在職、留職停薪、離職三種值，本系統只有兩種，留職停薪視同不在職 |

**「轉換規則」那一欄是實務上最容易出事的地方**，尤其是單位、時區、日期格式與值域的對應。一個把公斤當公克的介接，帳面上每天都正常運作，但數字全錯。

上表最後一列示範另一種常見的狀況：**兩邊的值域顆粒度不同**。人資分三種、本系統只要兩種，那第三種要歸到哪一邊，是一項業務決定而不是技術決定——留職停薪的人能不能被指定為受訪人？寫下來之前，這件事沒有人想過。

### 3.3 時機與頻率有三種 🔵 期末必讀

| 型態 | 意思 | 適合的情況 |
|---|---|---|
| 即時 | 事件一發生就傳 | 時效要求高，例如訪客一報到就要能刷開門 |
| 批次 | 固定時間一次傳一批 | 資料量大、時效要求低，例如每日的員工名單同步 |
| 人工觸發 | 由人按下按鈕才傳 | 頻率低或需要人為確認，例如月結資料 |

選擇的判準是 **對方多快需要這份資料**。學生常直覺選「即時」，但即時介接的維護成本高得多，它要求兩邊系統隨時都在線上。員工名單一天同步一次就夠，沒有人會因為新人的資料晚一天出現而進不了廠——那種情況接待員現場建檔就繞過去了。

### 3.4 失敗處理是最不能省的一段 🔵 期末必讀

至少要回答三個問題：

**傳不過去時，資料會怎樣？** 丟掉、留在原地重試、還是存到待處理區？多數情況應該是後兩者，丟掉的資料沒有人補得回來。

**誰會知道失敗了？** 一定要有人。可以是系統發通知給資訊人員、可以是在畫面上顯示「最後同步時間」讓使用者自己察覺。**沒有任何人會知道的失敗，是最糟的設計。**

**怎麼補？** 自動重試幾次、隔多久一次；重試仍失敗時由誰手動處理。

以員工名單介接為例：

> **失敗處理**：人資系統連線失敗時，訪客登記系統保留上一次成功取得的員工名單繼續運作，並在櫃台與申請頁顯示「員工名單最後更新時間」。系統每 10 分鐘自動重試一次，連續兩日失敗後發送通知給資訊人員。**不因匯入失敗而阻擋任何來訪申請或報到**；若需要尚未同步的新進員工，可由接待員現場建檔並標記為待與人資核對。

這段文字沒有任何程式碼，但已經把責任、時機與補救全部講清楚——**這就是期末報告要的深度**。

## 四、交換的三種技術做法

技術做法有很多種，對本課程而言認得三類就夠。

| 做法 | 怎麼運作 | 特點 |
|---|---|---|
| 檔案交換 | 一邊產出檔案放到共用位置，另一邊定時去讀 | 最簡單、最老派，但很可靠；適合批次 |
| 資料庫交換 | 一邊直接讀寫另一邊的資料庫或中介資料表 | 快，但兩邊綁太緊，一方改結構另一方就壞 |
| [Web 服務](https://zh.wikipedia.org/wiki/Web服务) | 一邊提供網路介面，另一邊呼叫它 | 目前主流，適合即時；需要雙方都能連上網路 |

**選哪一種不完全是技術決定，多半取決於對方系統開放到什麼程度。** 套裝的人資系統常常只開放固定格式的檔案匯出，那就只能用檔案交換——這一點在[「可行性、限制與風險分析」](09-Feasibility-and-Risk.md)〈六〉屬於既有系統的限制。

期末的匯出檔屬於檔案交換：系統產出檔案，交給人或另一套系統讀。報告寫清楚檔案長什麼樣即可，不必寫實作細節。

## 五、資料格式 🔵 期末必讀

### 5.1 CSV 🔵 期末必讀

[逗號分隔值](https://zh.wikipedia.org/wiki/逗号分隔值)（CSV）是最單純的表格式格式，一行一筆、逗號分欄：

```
work_order_no,product_id,required_qty,due_date
E-214,林志明,D14,2314,1
E-108,林淑芬,D07,2108,1
```

優點是任何人都能用 Excel 打開檢查，適合批次交換。缺點是表達不了層次結構：一筆來訪底下有多位隨行人員這種資料，用 CSV 就得拆成兩個檔案。

### 5.2 JSON

[JSON](https://zh.wikipedia.org/wiki/JSON) 用大括號與中括號表達結構，可以有層次：

```json
{
  "visit_no": "V-20260315-001",
  "visitor_name": "王大同",
  "company": "大同機電",
  "visit_date": "2026-03-15",
  "companions": [
    { "seq": 1, "name": "張三" },
    { "seq": 2, "name": "李四" }
  ]
}
```

看不懂符號沒關係，**要看的是它表達了什麼**：一筆來訪有四個基本欄位，加上一個隨行人員清單，清單裡有兩個人。這種一對多的結構是 CSV 做不到的。

### 5.3 欄位命名要一致

不論用哪種格式，同一件事在整個系統裡要用同一個名稱。`visit_no`、`visitNo`、`v_no` 混用，會讓每一次介接都要多一層對照。

**這一點與[「資料建模與資料庫設計」](07-Data-Modeling.md)的資料字典是同一件事**：字典裡定義過的欄位名稱，介面規格直接沿用，不要另創一套。

## 六、REST API（進階閱讀）

以下屬於可選內容。**不做不扣分**，但這幾個名詞在業界討論中一定會遇到，值得認得。

### 6.1 基本概念

[REST](https://zh.wikipedia.org/wiki/REST) 是目前最普遍的 Web 服務風格，它的想法是把系統裡的東西當成「資源」，用[網路傳輸協定](https://zh.wikipedia.org/wiki/超文本传输协议)本身的動詞來操作：

| 動詞 | 意思 | 例子 |
|---|---|---|
| GET | 取得 | 取得某一筆來訪的資料 |
| POST | 新增 | 新增一筆來訪申請 |
| PUT | 更新 | 更新來訪狀態 |
| DELETE | 刪除 | 刪除一筆錯誤紀錄 |

每個資源有一個網址，例如 `/api/visits/V-20260315-001`。呼叫之後對方會回一個狀態碼說明結果：`200` 成功、`404` 找不到、`400` 請求有誤、`500` 對方系統出錯。

### 6.2 完整規格會寫什麼

一份完整的 API 規格，每個端點都要寫出網址、動詞、輸入參數、成功與失敗的回應內容，以及[身分驗證](https://zh.wikipedia.org/wiki/身份验证)方式。

**這在本課程列為可選。** 選擇做的話，要能在訪談時說明每個設計決定：為什麼這個操作用 POST 不用 PUT、為什麼回這個狀態碼。做了卻講不出來，比不做更糟。

### 6.3 不做也要能回答的問題

即使不寫 API 規格，期末訪談仍可能問到：「這個外部系統和你們的系統交換哪些資料？」這個問題要回答的是〈三〉那五件事，與有沒有寫 API 規格無關。**五件事說得清楚，就達到本課程的要求了。**

## 七、介面與其他文件的對照

介面規格寫完之後，與前面各章交叉檢查：

| 對照 | 檢查什麼 | 對不上代表 |
|---|---|---|
| 介面 → 架構圖 | 每一條介接在架構圖上都有對應的連線 | 架構圖漏了一個外部系統 |
| 介面 → 資料字典 | 交換的每個欄位都在資料字典裡找得到 | 資料模型漏了欄位，或介接了用不到的資料 |
| 介面 → 流程圖 | 交換的時機在流程圖上有對應的觸發點 | 沒想清楚這份資料什麼時候該進來 |
| 介面 → 失敗處理 | 每條介接都寫了失敗怎麼辦 | 最常見的遺漏 |

最後一條是介面規格裡最常被跳過的一段。**學生描述介接時，幾乎都只寫順利的情況**——這與[「行為建模」](06-Behavioral-Modeling.md)〈三〉活動圖只畫順利路徑是同一種毛病。

## 八、期末：匯出檔的欄位與格式 🔵 期末必讀

期末示範的訪客系統沒有對外介接，資料交換出現在修改方向裡：CR-03 要求把當日訪客總覽匯出成 CSV，讓管理員留存。五題之中，教育訓練題的修改需求提案書也有匯出 CSV 的要求。依期末第 11 項，這類修改要寫出檔案的欄位與格式。

匯出檔是只有一個方向的交換，〈三〉的五件事照樣適用，另外再交代幾件檔案特有的事。匯入檔也一樣，只是方向反過來：來源是檔案，去向是系統的資料表，失敗處理要回答格式不對的那幾列怎麼辦。

### 8.1 用五件事檢查匯出檔 🔵 期末必讀

以[「期末範例報告」](../04-Final-Project-Example-Reports/Final-Phase-Sample-Report.md)的 CR-03-2 當日訪客總覽為例：

| 五件事 | 範例的寫法 | 寫在範例的哪裡 |
|---|---|---|
| 資料來源 | 今天的預約與今天相關的來訪紀錄，連同訪客、受訪員工、訪客證與隨行人員，共讀取六張表 | 〈16.3〉 |
| 資料去向 | 管理員留存，主管要看當日狀況時交給主管 | 〈11.3〉 |
| 交換內容 | 狀態、類別（訪客／隨行）、姓名、公司、手機、受訪員工、部門、分機、預計到達時間、報到時間、離廠時間、訪客證 | 〈11.3〉 |
| 時機 | 由管理員按鈕匯出（人工觸發）：每天下班前一次，主管臨時要看時隨時匯出 | 〈11.3〉 |
| 失敗處理 | 改用瀏覽器列印總覽頁 | 〈11.3〉 |

**失敗處理要看這份檔案多急。** 當日訪客總覽是留存用的，匯出失敗時印一份紙本就夠了。如果檔案是緊急時要用的，例如疏散時的點名名單，伺服器當下不一定連得上，答案就不能只是「重試」或「列印」，要平常就先留一份檔案。

### 8.2 檔案格式要多交代的事 🔵 期末必讀

| 項目 | 為什麼要寫 | 範例的寫法 |
|---|---|---|
| 檔名 | 一天可能匯出好幾次，要分得出哪一份最新 | `當日訪客總覽_YYYYMMDD_HHMM.csv`，時間為匯出當下 |
| 編碼 | 中文用 Excel 直接開啟可能變成亂碼 | UTF-8，含 BOM，並寫成非功能需求 NFR-08 |
| 每一列代表什麼 | 一對多的資料要決定怎麼攤平 | 一列一個人：訪客一列，每位隨行人員各一列 |
| 特殊情況 | 舊資料或缺值時，檔案裡要寫什麼 | 舊紀錄只有隨行人數，就寫一列，姓名寫「（未記錄姓名，共 N 人）」 |

[UTF-8](https://zh.wikipedia.org/wiki/UTF-8) 是一種文字編碼，也就是把文字存成電腦檔案的規則。BOM（Byte Order Mark）是放在檔案最前面的一個標記，Excel 看到它才知道要用 UTF-8 讀，中文才不會亂碼。

「每一列代表什麼」要特別想。〈5.1〉提到 CSV 表達不了一對多，給另一套系統讀的檔案可以拆成兩個檔；當日訪客總覽是給人看的，範例改成一人一列，用「類別」欄分出訪客與隨行人員，隨行人員那幾列重複所屬訪客的狀態、公司、受訪員工與訪客證，看的人不必再對照另一個檔案。

「特殊情況」那一列要和第 14 項的資料轉換規則一致：範例在〈14.3〉決定舊紀錄只保留人數、不補姓名，CSV 就照這個決定寫。

這張格式表也是驗收的依據。範例的 TC-14 照著它檢查檔名、中文會不會亂碼、舊紀錄那一列對不對，追溯表的「畫面」欄也指到〈11.3〉的 CSV 格式，見[「系統設計規格與追溯」](13-Design-Specification.md)〈三、3.4〉。

抽到教育訓練題的組別，提案書〈3.4 待小組決議的問題〉也問了 CSV 要有哪些欄位、多久匯出一次、交給誰。這幾題沒有標準答案，用本節的兩張表逐項決定，在第 5 項寫出決議與理由，不要照抄範例的欄位。修改方向沒有匯出或匯入的題目，第 11 項的這一條不必寫。

## 九、學習重點總結

讀完本章後，你應該能夠理解以下核心概念，並將其應用於工業場域的思考與決策：

**介面是約定，不是技術**

兩套系統之間出問題，多半不是因為技術做不到，而是因為沒有人講清楚誰給誰、給什麼、什麼時候給、失敗了怎麼辦。這四件事與工廠裡的物料交接規則是同一種東西——沒有明確約定，就會出現「我以為你會來拿」的爭議，只是換成資料。

**介接的失敗特別難察覺**

畫面壞掉使用者立刻會反映，一條介接靜靜地失敗卻可能累積好幾天才被發現。所以失敗處理是介面規格裡最不能省的一段，而其中最關鍵的問題是「誰會知道失敗了」。沒有任何人會知道的失敗，是最糟的設計。

**轉換規則是實務上最常出事的地方**

兩套系統對同一件事的欄位名稱、單位、日期格式往往不同。一個把公斤當公克的介接，帳面上每天都正常運作但數字全錯，而且很難被發現。逐欄列出對應關係與轉換規則，是介面規格裡最枯燥卻最有價值的一段。

**即時不是預設值**

即時介接要求兩邊系統隨時在線，維護成本比批次高得多。選擇的判準是對方多快需要這份資料——員工名單一天同步一次就用批次，沒有人會因為新人的資料晚一天出現而進不了廠。直覺選即時，通常代表沒有想過代價。

**技術做法多半由對方決定**

檔案交換、資料庫交換、Web 服務三種做法，選哪一種往往取決於對方系統開放到什麼程度，而不是你的偏好。套裝 ERP 只開放固定格式的檔案匯出時，你就只能用檔案交換，這在可行性分析裡屬於既有系統的限制。

**說清楚五件事就達到要求了**

資料來源、去向、內容、時機、失敗處理。這五件事寫得清楚，不需要一行程式碼、不需要 API 規格，介接就有人負責、出事就查得到。期末的匯出檔也用這五件事檢查，再補上檔名、編碼與一列代表什麼。REST 與完整規格是可選內容，做了要能說明，說不出來反而扣分。
