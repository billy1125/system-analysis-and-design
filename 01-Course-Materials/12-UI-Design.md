# 使用者介面設計

介面是整套系統唯一被使用者看見的部分。前面十一章做的所有工作——需求、流程、資料、架構、介接——對站在廠外用手機填申請的訪客來說都不存在，他只會遇到眼前這個畫面。畫面上少一個欄位，他就少一項資訊；多一個他填不出來的必填欄位，他就會亂填。

這一章要講的不是怎麼把畫面做得好看。**介面設計在本課程的真正用途，是拿來驗證前面所有的分析對不對。** 一個需求如果沒有想清楚，畫成畫面時就會卡住：這個欄位的值從哪來？按下送出之後使用者怎麼知道成功了？這批資料要顯示在哪一頁？**畫面是分析錯誤最誠實的照妖鏡**，因為它逼你把每一件事具體到「使用者到底看到什麼」。

依[「報告內容」](../00-Course-Introduction/Report-Contents.md)期末第 6 項，這一項明訂 **不評美術**：Figma、AI 生成靜態網頁、簡報拉方框、紙筆手繪拍照上傳，都同樣計分。老師看的是畫面上有哪些欄位與按鈕、這些欄位從哪來、按下去會發生什麼事。

> **前情提要**：本章假設你已完成前面各章的需求、流程與資料設計。畫面上的每一個欄位都應該追溯得到[「資料建模與資料庫設計」](07-Data-Modeling.md)的資料字典，每一個按鈕都應該對應到[「行為建模」](06-Behavioral-Modeling.md)的某一個流程步驟。

> **延伸閱讀**：本章不教任何繪圖工具的操作。工具只是產出媒介，換一套工具不影響這一章講的任何原則。

> **期末必讀標記**：標題後加註 🔵 期末必讀 的小節，是期末小組報告八項產出直接會用到的內容。判準見[「系統設計範例報告說明」](../04-Final-Project-Example-Reports/Design-Phase-Deliverables.md)，成品的樣子見[「系統設計範例報告」](../04-Final-Project-Example-Reports/Design-Phase-Sample-Report.md)。未標記的小節仍屬課程範圍，只是期末不會直接產出。

## 一、介面設計不是美工 🔵 期末必讀

### 1.1 三件不同的事 🔵 期末必讀

「UI 做得好不好」這句話其實混了三件事：

| 面向 | 在問什麼 | 本課程 |
|---|---|---|
| 視覺（Visual） | 好不好看、配色與排版 | 不評 |
| 使用性（Usability） | 好不好用、會不會操作錯誤 | 評 |
| 資訊完整性 | 該有的資訊與功能有沒有到位 | 評 |

**這門課評的是後兩項。** 一張手繪的線框圖，只要欄位齊全、流程說得通，分數會高於一張配色精美但少了三個必要欄位的高保真原型。

### 1.2 為什麼工管背景做這件事有優勢

介面設計的核心問題是「使用者在什麼情境下、要完成什麼任務、需要哪些資訊」。這正是工作研究在問的事——動作經濟原則、作業標準、人因工程，講的都是怎麼讓人在特定條件下把事情做對做快。

**把畫面當成一個作業站來看**：使用者站在這裡要完成一件事，需要哪些資訊在手邊、要做幾個動作、哪些步驟可以省掉、哪裡容易做錯。這個思考方式比研究配色有用得多，也是你已經會的東西。

## 二、使用性原則

### 2.1 十項啟發式

[使用性](https://zh.wikipedia.org/wiki/可用性)（Usability）最通行的檢查表是 Nielsen 在 1994 年整理的十項啟發式（Heuristics）。它們不是規則，是拿來檢查介面的十個角度：

| 原則 | 意思 | 報到畫面的例子 |
|---|---|---|
| 系統狀態可見 | 讓使用者知道現在發生什麼事 | 送出後顯示「已報到，訪客證 V-018，目前在廠 7 人」 |
| 貼近真實世界 | 用使用者的語言，不用系統術語 | 寫「要找誰」不寫「受訪人工號」 |
| 使用者控制與自由 | 做錯了能回頭 | 送出後 30 分鐘內可自行修正 |
| 一致性 | 同樣的東西在各頁長得一樣 | 所有頁面的「送出」都在右下角 |
| 預防錯誤 | 從源頭避免出錯 | 數量欄位只能輸入數字 |
| 辨識勝於回憶 | 選項列出來，不要讓人背 | 受訪人用搜尋後點選，不要讓訪客背工號 |
| 彈性與效率 | 熟手有捷徑 | 支援掃碼直接帶入，不必逐欄鍵入 |
| 簡潔的設計 | 不放不需要的東西 | 現場畫面不顯示成本資訊 |
| 錯誤訊息要有用 | 說明問題並指出怎麼辦 | 「此證由王大同使用中，請換一張」 |
| 說明與文件 | 需要時找得到協助 | 畫面上有操作說明的連結 |

**其中對本題最關鍵的是「辨識勝於回憶」與「預防錯誤」。** 訪客第一次用、沒有人教、單手拿著手機；接待員在尖峰時段一次要處理八個人。任何需要記憶或精確輸入的設計都會出錯。

### 2.2 拿它當檢查表用

十項不必背，用法是畫完畫面之後逐項對照一次。**每一項問「我的畫面在這一點上做到了嗎」**，答不出來的那幾項就是要改的地方。這比憑感覺調整有效得多。

期末報告不必逐項寫出檢查結果，但如果某個設計決定是為了滿足其中一項，值得寫出來：「受訪人改為搜尋後點選而非自由輸入姓名，是為了避免訪客把名字寫錯導致找不到人，也讓來訪紀錄真的連得到員工。」

**但「列出來給人挑」不等於「用下拉選單」。** 全廠三百多人，下拉選單捲不完；而且那份名單一旦送到訪客的瀏覽器上，等於整份員工名冊公開了。同樣的原則在這裡要改用「輸入兩個字、伺服器回傳最多十筆」來實現。**十項啟發式給的是方向，落地成哪一種元件由現場條件決定**，見〈六〉。

## 三、從需求與流程推出畫面 🔵 期末必讀

### 3.1 畫面不是憑空想的 🔵 期末必讀

學生最常見的做法是打開工具開始拉方框，想到什麼放什麼。正確的做法是從前面的產出推導出來。

**從使用案例推出要有哪些畫面。** 一個使用案例通常對應一到三個畫面。UC-01「辦理訪客報到」對應的是調出申請的畫面與報到確認畫面。

**從活動圖推出畫面之間怎麼走。** 活動圖上的每一個判斷節點，在介面上都會變成一個分支：條碼無效要顯示什麼、數量超量要跳出什麼。

**從資料字典推出每個畫面有哪些欄位。** 要輸入的欄位來自資料字典中標示「使用者輸入」的那些；要顯示的欄位來自那些「系統產生」或「計算得來」的。

### 3.2 資訊架構與導覽

畫面多起來之後，要決定它們怎麼組織。判準是 **依角色與任務分組**，不是依資料表分組。

| ❌ 依資料表 | ✅ 依任務 |
|---|---|
| 來訪紀錄管理、訪客管理、訪客證管理 | 我要辦報到、我要查在廠有誰、我要維護基本資料 |

第二種分法的好處是使用者找得到——接待員想的是「我要幫這個人辦報到」，不是「我要操作來訪紀錄資料表」。

**導覽層次不要超過三層。** 現場使用者要在三次點擊之內到達最常用的功能；如果做不到，代表分組有問題。

### 3.3 一張畫面清單 🔵 期末必讀

期末報告建議附一張畫面清單，這張表也是後續檢查的基礎：

| 畫面 | 使用角色 | 對應使用案例 | 主要功能 |
|---|---|---|---|
| 櫃台報到 | 接待員 | UC-01 | 調出申請、輸入訪客證、送出 |
| 在廠訪客查詢 | 接待員、職安人員 | UC-06 | 依日期或受訪單位查詢 |
| 離廠登記 | 接待員 | UC-02 | 登記離廠時間與收回訪客證 |
| 基本資料維護 | 系統管理員 | UC-08 | 維護訪客證、員工、部門 |

**最後一列不要漏。** 基本資料維護的畫面是最常被忘記的，這與[「資料建模與資料庫設計」](07-Data-Modeling.md)〈三、3.2〉CRUD 矩陣「整欄沒有 C」是同一個問題的兩面。

## 四、線框圖、原型與保真度 🔵 期末必讀

### 4.1 三種保真度

| 保真度 | 長什麼樣 | 適合什麼時候 |
|---|---|---|
| 低保真（線框圖） | 方框與線條，只有結構與欄位 | 討論資訊架構與流程 |
| 中保真 | 有版面配置、真實文字，但沒有互動 | 確認畫面內容是否齊全 |
| 高保真（原型） | 接近成品，可點擊操作 | 使用者測試、驗收前確認 |

**保真度越低，別人越敢批評。** 一張手繪的草圖，使用者會直接說「這裡不對」；一個做得精美的高保真原型，使用者會覺得「都做成這樣了，不好意思要求改」。這個現象在實務上很普遍，也是低保真線框圖在早期階段更有價值的原因。

### 4.2 本課程的要求 🔵 期末必讀

期末報告要求的是 **主要畫面的線框圖或原型**，保真度不拘。判斷夠不夠的標準是三個問題：

- 畫面上有哪些欄位與按鈕？
- 這些欄位的資料從哪裡來、要存到哪裡？
- 按下每個按鈕會發生什麼事？

**三個問題答得出來，手繪拍照上傳也完全合格。** 反過來，用專業工具做出來但答不出這三題，一樣不及格。

### 4.3 不必畫每一個畫面 🔵 期末必讀

挑主要的畫。判準是：**每個角色至少一個、每個核心使用案例至少一個、有分支或例外的至少一個。** 增刪改查四個長得差不多的畫面，畫一個代表即可，其餘用文字說明差異。

## 五、畫面欄位對回資料字典 🔵 期末必讀

這一節是期末報告第 8 項追溯鏈的最後一段，也是本章最能拉開分數的地方。

### 5.1 逐欄對照 🔵 期末必讀

對每一個主要畫面，做一張欄位對照表：

| 畫面欄位 | 顯示或輸入 | 對應資料 | 備註 |
|---|---|---|---|
| 來訪編號 | 輸入 | 來訪紀錄.visit_no | 讀取，不可修改 |
| 訪客姓名 | 顯示 | 訪客.visitor_name | 由來訪帶出 |
| 公司 | 顯示 | 訪客.company | 唯讀 |
| 目前在廠人數 | 顯示 | **不存**，由狀態為已報到的來訪紀錄計數 | 推導值 |
| 訪客證編號 | 輸入 | 來訪紀錄.pass_id | 必填，須為未被佔用的證 |
| 該證可不可發 | 顯示 | **不存**，由訪客證與來訪紀錄兩表推導 | 推導值 |
| 報到時間 | 不顯示 | 來訪紀錄.checkin_at | 系統自動帶入 |

**第四列與第六列那種「畫面上看得到、資料表裡卻沒有」的東西要特別處理。** 在廠人數、停留時間、是否逾時、某張證可不可發，這幾類值多半是算出來的而不是存下來的（判準見[「資料建模與資料庫設計」](07-Data-Modeling.md)〈四、4.3〉）。它們在對照表上不能留白，也不能硬指一個不存在的欄位，要標成推導值並寫出算式的來源。畫面上的數字愈多，這件事愈值得另外整理成一張推導欄位清單，見[「資料建模與資料庫設計」](07-Data-Modeling.md)〈七、7.2〉。

### 5.2 這張表會抓出三種錯誤 🔵 期末必讀

**畫面上有欄位，資料字典與推導欄位清單兩邊都找不到。** 代表資料模型漏了東西，或這個欄位其實不該出現。

**資料字典裡標「使用者輸入」，但沒有任何畫面可以輸入它。** 代表少了一個畫面或一個欄位——這份資料永遠會是空的。

**要求使用者輸入他手上沒有的資料。** 這是最實際的一種錯誤。訪客的申請畫面上如果有「受訪人工號」要他填，就要問：他手上只有一張名片，怎麼知道對方的工號？

第三種與[「行為建模」](06-Behavioral-Modeling.md)〈七〉那條「循序圖 → 介面欄位」的檢查是同一件事，只是從畫面這一端反過來查。

## 六、現場的介面限制 🔵 期末必讀

一般的介面設計教材預設使用者坐在辦公室、用滑鼠鍵盤、雙手空閒、環境安靜。**工廠現場一項都不成立。**

| 限制 | 對設計的影響 |
|---|---|
| 戴手套操作 | 按鈕要大、間距要寬；電容式觸控可能完全無反應。**本題不適用，但仍要問過** |
| 環境噪音 | 不能依賴提示音，要用顏色與大字回饋 |
| 光線 | 強光下螢幕反光，對比要高、不要用淺灰色文字 |
| 油污與粉塵 | 螢幕會髒、觸控會失準，操作步驟要少 |
| 站姿操作 | 沒有地方放東西，不能要求同時看紙本 |
| 雙手常常不空 | 訪客常提著東西，操作要單手可完成，主要按鈕放在拇指構得到的位置 |
| 無鍵盤 | 盡量用掃碼、大方塊按鈕、數字鍵盤，避免文字輸入與下拉選單 |
| 網路不穩 | 送出後要明確顯示成功或失敗，不能靜靜地失敗；**訪客在廠外只有行動網路** |
| 螢幕尺寸 | 訪客的手機只有 5 到 6 吋直式，一頁放不了太多欄位 |
| **使用者熟悉度** | **一年只用兩次的人，沒有機會變熟練**。每個欄位都要有標籤與提示，不用專有名詞 |

**這張表要逐項問過，把答案與影響都寫進報告，即使某幾列的答案是「不適用」。** 問過並寫下答案，跟根本沒想過，在文件上看得出差別。**答案還要在畫面上看得到回應**——一張在工廠現場用的畫面如果長得跟辦公室的一模一樣，就代表這張表只是抄上去的。

**這一節是工管背景的人最有貢獻的地方。** 資訊人員很難憑空知道大門白天會不會日照直射、尖峰時段一次來幾個人。期末報告如果題目在工業現場，這些限制要在畫面設計裡看得到回應——而不是只在限制清單裡列一行。

**最後一列是本題特有、而產線題目沒有的一項。** 產線的使用者天天用同一套系統，可以靠熟練度彌補設計缺陷；訪客一輩子只用兩三次，沒有第二次機會。這個差別會改變整個介面的取向：產線畫面可以為了快而犧牲說明，這裡不行。

如果你的題目不在工廠（例如校園器材借用系統），同樣的思路要換成那個場域的限制：使用者是用手機還是電腦、在什麼情境下操作、會不會趕時間。

## 七、原型怎麼被使用與評估 🔵 期末必讀

### 7.1 原型是拿來發現問題的

原型最大的價值不是展示，是 **在還很便宜的時候發現需求錯誤**。

一份需求文件拿給沒有資訊背景的接待員看，他讀完通常說不出什麼意見；同樣的內容做成畫面讓他點三分鐘，他馬上會說「這裡不對，我們不是這樣做的」「這個欄位我填不出來」。**這是原型法在[「系統分析與設計導論」](01-Systems-and-Analysis.md)〈五、5.2〉被提到的原因**，也是它在製造現場特別有效的原因。

### 7.2 評估看什麼 🔵 期末必讀

期末報告的這一項，評的是三件事：

| 評什麼 | 具體看 |
|---|---|
| 資訊是否完整 | 使用者完成任務所需的資訊都在畫面上嗎 |
| 操作是否合理 | 步驟數合不合理、錯誤能不能回頭、符不符合現場條件 |
| 與其他文件是否一致 | 欄位對得上資料字典嗎、流程對得上活動圖嗎 |

**不評的是**：配色、字體、圓角、動畫、視覺風格。

### 7.3 說明要跟著畫面走 🔵 期末必讀

每一張畫面要附上一份說明，欄位如下：

| 欄位 | 說明 |
|---|---|
| 畫面名稱與編號 | 編號要能被追溯鏈引用 |
| 服務角色 | 哪些角色看得到這個畫面 |
| 對應需求 | FR 與 NFR 編號 |
| 對應流程 | 對應到哪一張活動圖的哪一段 |
| 畫面欄位 | 每一欄的名稱、可否編輯、資料來源 |
| 操作與後果 | 每一顆按鈕按下去會發生什麼、去哪一頁 |
| 依身分的差異 | 同一個畫面對不同角色顯示的差別 |

**最常漏的是最後兩欄。** 畫了按鈕卻沒說按下去會怎樣，資訊人員照著做不出來；而「同一張清單，生管看得到但主管才有核准鈕」這種差異不寫下來，實作時就會變成兩個人各自猜一套權限。**按鈕的出現條件本身就是一項設計決定**，要寫在「操作與後果」那一欄裡。

只放一堆截圖而沒有說明，讀者無法判斷你有沒有想過那些欄位——而訪談時「這個畫面中的欄位，在資料庫中儲存在哪一個資料表」正是最常見的追溯題。

## 八、學習重點總結

讀完本章後，你應該能夠理解以下核心概念，並將其應用於工業場域的思考與決策：

**畫面是分析錯誤最誠實的照妖鏡**

畫面逼你把每一件事具體到「使用者到底看到什麼」，而具體不出來的地方，就是前面某一章沒想清楚的地方。這是介面設計被排在最後一章的理由：它不新增分析，它驗收分析。一個欄位對不上任何資料表、一個按鈕說不出按下去會發生什麼，要回頭改的都不是畫面，是資料設計或流程設計。

**這門課評使用性與資訊完整性，不評視覺**

一張手繪的線框圖只要欄位齊全、流程說得通，分數會高於配色精美但少三個必要欄位的高保真原型。判斷夠不夠只有三個問題：有哪些欄位與按鈕、資料從哪來到哪去、按下去會發生什麼事。答得出來，紙筆拍照上傳也合格。

**把畫面當成一個作業站來設計**

使用者站在這裡要完成一件事，需要哪些資訊在手邊、要做幾個動作、哪裡容易做錯——這正是工作研究在問的問題。動作經濟、作業標準、人因工程的思考方式，用在介面上比研究配色有效得多，而那是工管背景已經會的東西。

**保真度越低，別人越敢批評**

手繪草圖使用者會直接說哪裡不對；做得精美的高保真原型，使用者反而會覺得不好意思要求修改。這個現象讓低保真線框圖在早期階段更有價值——原型的目的是在還很便宜的時候發現需求錯誤，不是展示成果。

**每個畫面欄位都要對得回資料字典**

逐欄對照會抓出三種錯誤：畫面上有而字典裡沒有的欄位、字典裡標使用者輸入卻沒有地方輸入的欄位，以及要求使用者提供他手上根本沒有的資料。第三種最實際——訪客手上只有一張名片，怎麼會知道對方的員工工號。

**現場條件會推翻一般的介面慣例**

噪音、強光、單手操作、小螢幕、行動網路、使用者永遠不會變熟練，工廠現場少有幾項符合辦公室的預設。這些限制要在畫面設計裡看得到回應，而不是只在限制清單裡列一行；**即使某幾項的答案是「不適用」，逐項問過並寫下來，跟根本沒想過在文件上看得出差別**。這也是工管背景在介面討論中最有貢獻的地方——資訊人員很難憑空知道那個場域的實際作業條件。
